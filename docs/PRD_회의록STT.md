# 회의 녹음 전사(STT) + 화자 분리 기능 PRD

문서 성격: 내비온 견적서 생성기 **회의록 기능의 입력단 확장**을 위한 제품 요구사항 정의서(내부용).

작성 근거: 현행 코드 실측(`src/api/minutes.py`, `src/ai/minutes.py`, `src/convert/attach.py`, `src/convert/kordoc.py`, `ui/index.html`) + 기존 문서 관행(`docs/PRD_영수증OCR.md`) + GitHub 탐색 결과(`docs/research_회의록STT_20260819/report.md`, 사실 F001~F015) + 1차 파일럿 실측(`docs/research_회의록STT_20260819/pilot_result.md`).

**v0.2 갱신(2026-08-19)**: 엔진 후보 탐색을 마쳐 §7.2·§7.6·§10을 확정/갱신했다. 남은 `[확인 필요]`는 실측(파일럿)으로만 풀 수 있는 항목뿐이다.

**v0.3 갱신(2026-08-19)**: 전사본 분량 상한(Q3)을 1안으로 확정·구현했고, Phase 1 모듈·API·UI 착수를 반영했다. 파일럿 게이트(Q5~Q7·Q9)는 아직 미완이다.

**v0.4 갱신(2026-08-20)**: 합성음 1차 파일럿 수치(Q6·Q7·Q9)와 배포 빌드 방침(엔진 패키지 exe 미동봉)을 반영했다. 게이트는 통과시키지 않았고, 실제 회의 녹음 실측이 남는다.

### 1.2 제품 요약

회의록 화면에 **녹음 파일(m4a/mp3/wav 등)을 그대로 드롭**하면, 앱이 음성을 텍스트로 받아쓰고(한국어·영어 혼용 포함), **누가 말했는지(화자)를 구분한 전사본**을 만들어, 기존 회의록 AI 초안 파이프라인에 자동으로 투입한다. 사용자는 전사본을 확인·수정하고 화자에 실명을 붙인 뒤, 지금과 똑같이 회의록 HWPX를 생성한다.

한 줄 요약: **"외부 STT 앱에서 txt를 뽑아 붙여넣던 수작업을 앱 안으로 들여온다."**

### 1.3 배경 — 왜 지금 내재화인가

현행 회의록 기능은 이미 "녹음 전사본을 붙여넣는 것"을 전제로 설계돼 있다. UI 문구가 그 증거다.

- `ui/index.html:268` — "녹음 전사본을 그대로 붙여넣어도 됩니다."
- `ui/index.html:272` — 파일 첨부 설명이 "녹음 전사본·메모·자료"
- `src/api/minutes.py:30` — 오류 메시지가 "회의 메모를 5자 이상 입력하거나 **녹음**·메모 파일을 첨부하세요"

즉 제품은 이미 녹음을 상정하지만, **정작 음성 파일 자체는 받지 못한다.** 첨부 변환기(kordoc)의 지원 확장자는 문서 계열뿐이다(`src/convert/kordoc.py:44` — `.hwp .hwpx .hml .pdf .docx .xlsx .xls`, 패스스루 `.txt .md .markdown`). 그 결과 실무자는 매번 다음을 한다.

```
녹음(m4a) → [외부 STT 앱] → txt 저장 → 앱에 드롭 → 회의록 초안
             └─ 앱 밖 왕복. 화자 구분 품질도 외부 앱에 종속.
```

내재화의 실익은 세 가지다.

1. **왕복 제거** — 파일 하나 드롭으로 끝난다.
2. **화자 구분의 회의록 직결** — 화자 라벨이 붙으면 `participants`(참석자) 슬롯과 발언 귀속을 AI가 훨씬 정확히 채운다. 현행 스키마는 이미 기관별 참석자 줄 목록과 "기관/담당자별 할 일"을 요구한다(`src/ai/minutes.py:32-42, 81`). 화자 정보가 없으면 이 부분은 사실상 사용자가 손으로 채워야 한다.
3. **대외비 통제** — 정부지원사업 회의 녹음은 미공개 기술·단가·인건비가 오간다. 외부 STT 앱/클라우드로 원본 오디오가 나가는 현재 경로는 통제 밖이다. 로컬 처리 선택지를 제품이 직접 제공하면 이 판단을 사용자가 앱 안에서 내릴 수 있다.

기술적 착수 비용도 낮은 편이다. **외부 엔진을 exe 옆에 런타임 설치하고 사용자 버튼으로 갱신·롤백하는 선례가 이미 있다** — kordoc 연동(`src/convert/kordoc.py`: `kordoc-runtime/` 폴더, npm 설치, 스모크 변환 후 실패 시 직전 버전 복구). 로컬 STT 엔진도 같은 골격을 재사용할 수 있다.

## 2. 목표와 비목표

### 2.1 사업 목표

- 회의 종료부터 회의록 초안까지의 소요 시간을 단축한다(외부 앱 왕복 제거).
- 화자 정보를 확보해 참석자·발언 귀속·할 일 배정의 초안 품질을 올린다.
- 대외비 녹음의 외부 전송 여부를 사용자가 통제 가능하게 만든다.

### 2.2 사용자 목표

- m4a 녹음 파일 하나를 드롭하면 회의록 초안까지 이어지길 원한다.
- 한국어 회의 중간에 섞이는 영어 기술 용어·문장이 뭉개지지 않길 원한다.
- "화자1/화자2"에 실제 이름을 붙여 회의록 참석자·발언에 반영하고 싶다.
- 1~2시간짜리 긴 회의도 실패 없이 처리되고, 진행 상황이 보이길 원한다.

### 2.3 비목표 (Non-goals)

- **앱 내 실시간 녹음(마이크 캡처)·실시간 자막** — 파일 입력만 다룬다. 녹음은 사용자의 폰/기존 도구로 한다. (P2 후보, §4.2 FR-22)
- **화자 성문 등록·재식별(speaker ID DB)** — "이 목소리는 항상 김OO"처럼 사람을 영구 식별하는 기능은 만들지 않는다. 개인정보(생체정보) 성격이 강하고, 회의록 작성에는 세션 내 화자 분리만으로 충분하다. 매 회의마다 사용자가 이름을 붙인다.
- **자체 음성 모델 학습·파인튜닝** — 착수하지 않는다.
- **완전 무인 자동 반영** — 전사본을 사용자 확인 없이 회의록으로 확정하지 않는다. 기존 "AI 초안 → 검토 → 확정" 게이트를 그대로 유지한다.
- **다국어 전면 지원** — 대상은 한국어·영어(및 그 혼용)뿐이다. 그 외 언어는 "동작할 수도 있음" 수준으로 두고 보장하지 않는다.

## 3. 사용자 페르소나

`docs/PRD_영수증OCR.md` §3과 동일한 단일 페르소나(로그인·서버 없는 개인 데스크톱 앱)를 따른다.

| 항목 | 내용 |
|---|---|
| 이름(가칭) | 사업관리 실무자 |
| 역할 | 정부지원사업 회의 주관·기록, 회의록 제출 |
| 기술 수준 | 일반 사무 사용자. CLI·파이썬 비사용. GPU 유무를 모를 수 있음 |
| 주 사용 맥락 | 회의 직후, 폰/노트북 녹음(m4a) 파일을 가진 상태 |
| 핵심 불편 | 외부 STT 앱 왕복, 화자 구분 수작업, 긴 회의 전사의 지루한 정리 |
| 성공 기준 | "받아쓰고 정리하기"가 "훑어보고 이름 붙이기"로 바뀌는 것 |

### 3.1 접근·권한 모델 (보안 접근)

로그인이 없으므로 전통적 인증/인가 대신 다음이 보안 요구사항을 대신한다(스토리 US-012~US-014).

- 오디오가 **외부로 나가는 경로를 쓸 때만** 사전 고지하고, 기본값은 사용자가 명시적으로 고른 모드를 따른다.
- 전사 원문·오디오 사본은 사용자 작업 폴더 밖에 함부로 남기지 않는다. 임시 파일은 처리 후 삭제한다.
- API 키는 기존 DPAPI 암호화 저장 자산을 그대로 쓴다.

## 5. 사용자 경험(UX) 흐름

### 5.1 진입점

회의록 뷰의 **기존 첨부 드롭존 그대로**. 신규 사이드바 항목을 만들지 않는다 — 사용자에게 이것은 "새 기능"이 아니라 "첨부에 녹음 파일이 추가된 것"이어야 한다.

### 5.2 핵심 경험

```
[1] 회의록 뷰 → 첨부 드롭존에 회의녹음.m4a 드롭
      │  (최초 1회) 엔진 미설치 배너 → [설치] 클릭 → 모델 다운로드 진행률
      ▼
[2] 전사 진행 (취소 가능)
      │  ① 오디오 표준화(→wav 16kHz mono)  ② 전사  ③ 화자 분리
      │  진행률: "전사 중 34% — 00:21:40 / 01:03:12"
      ▼
[3] 전사 검토 화면
      ┌──────────────────────────────────────────────┐
      │ 화자 이름 지정                                │
      │  화자1 [내비온 김형일 ▾]  화자2 [KIST 김종민 ▾]│
      ├──────────────────────────────────────────────┤
      │ [00:00:12] 화자1: 오늘 안건은 라이다 센서…      │
      │ [00:00:31] 화자2: TRL 기준으로 보면 level 5… │
      │ [00:01:02] 화자1: 그 부분은 [확인 필요]        │  ← 저신뢰 구간 표시
      └──────────────────────────────────────────────┘
      ▼
[4] [이 전사본으로 회의록 초안 만들기]
      ▼
[5] 기존 회의록 AI 초안 → 검토 팝업 → HWPX 생성  (변경 없음)
```

### 5.3 상태·예외 경험

- **엔진/모델 미준비**: 드롭 즉시 실패시키지 않고, 배너로 설치를 유도한 뒤 대기열에 파일을 유지한다.
- **긴 회의**: 예상 소요 시간을 먼저 고지("약 8~15분 예상"). 취소 시 부분 결과라도 보존할지 물어본다.
- **무음/잡음 파일**: 세그먼트가 거의 없으면 "음성을 인식하지 못했습니다 — 파일·언어 확인" 안내.
- **화자 과다 추정**: 실제 3명인데 화자7까지 나오는 경우가 흔하다. 검토 화면에서 **화자 병합(화자5 → 화자2)** 을 지원한다. (P1)
- **오프라인**: 로컬 모드는 오프라인 동작을 보장한다. 클라우드 모드는 네트워크 필요를 고지한다.

```jsonc
  "languages": ["ko", "en"],

    { "id": "S1", "label": "화자1", "name": "내비온 김형일", "speak_sec": 1420 }
  ],
  "segments": [
    { "start": 12.4, "end": 19.8, "speaker": "S1", "text": "오늘 안건은…", "lang": "ko", "confidence": 0.91 }
  ],
  "warnings": ["low_confidence:00:34:10-00:34:40"]
}
```

### 6.2 회의록 AI 입력 포맷

`draft_minutes`에 넘길 때는 화자 이름이 반영된 평문으로 직렬화한다. 이름 미지정 화자는 `화자N` 그대로 둔다(추측 금지 원칙).

```
[00:00:12] 내비온 김형일: 오늘 안건은 라이다 센서 단가입니다.
[00:00:31] KIST 김종민: TRL 기준으로 보면 level 5 정도입니다.
```

타임스탬프 포함 여부는 토큰 비용과 초안 품질의 트레이드오프 — 파일럿에서 결정한다. `[확인 필요]`

## 7. 기술 설계 개요

### 7.1 모듈 골격 (회의록·영수증 선례 동형)

```
src/stt/                  # 음성 도메인
    __init__.py
    engine.py             # 엔진 추상화: transcribe(path, opts) -> segments
    audio.py              # ffmpeg 등으로 표준화(wav 16kHz mono) · 길이 산출 · 청크 분할
    diarize.py            # 화자 분리 + 세그먼트 병합
    runtime.py            # 엔진/모델 설치·버전·갱신 (kordoc.py 골격 이식)
    serialize.py          # segments -> 회의록 AI 입력 텍스트 / .transcript.txt
src/api/stt.py            # SttApi 믹스인 — 전사 시작·진행·취소·화자매핑 엔드포인트
```

조립 지점(기존 파일 최소 수정):
- `src/api/__init__.py`: `Api(...)` 상속 목록에 `SttApi` 추가.
- `src/convert/kordoc.py`: 음성 확장자를 kordoc에 보내지 않도록 분기(변환 대상에서 제외하고 STT로 라우팅).
- `ui/app.js`: `convertInto` 경로에서 음성 파일은 STT 경로로 분기.

### 7.2 최대 쟁점 — 엔진 배치 방식 (**미결정, GitHub 탐색으로 판정**)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 로컬 엔진 동봉/런타임 설치** | 전사·화자분리 모델을 사용자 PC에서 실행 | 오프라인 동작, 대외비 녹음이 밖으로 안 나감, 건당 비용 0 | 모델 파일 수백 MB~수 GB, CPU에서 느림, 설치 실패 지원 부담 |
| **B. 클라우드 STT API** | 오디오를 API로 전송 | 빠름, 배포 부피 0, 화자분리 API 제공사 다수 | **회의 녹음 원본이 외부로 전송**, 건당 비용, 오프라인 불가 |
| **C. 하이브리드(모드 토글)** | 기본 로컬, 사용자가 클라우드 선택 | 상황별 최적, 대외비 회의는 로컬 | 구현·테스트 2배, UI 복잡도 |

**참고 — 영수증 PRD와의 관계**: 영수증에서는 로컬 OCR 동봉을 배포 부피를 이유로 비목표로 배제했다(`docs/PRD_영수증OCR.md:48`). 회의 녹음은 전제가 다르다. (1) 영수증 이미지보다 **회의 녹음의 대외비 민감도가 훨씬 높고**, (2) 한국어 로컬 음성 모델은 한국어 로컬 OCR과 달리 실사용 가능한 공개 가중치가 존재할 가능성이 크며(`[확인 필요]`), (3) kordoc 선례로 **"동봉하지 않고 런타임에 받는"** 배포 경로가 이미 검증돼 있어 exe 부피 문제를 우회할 수 있다. 따라서 로컬 배제를 그대로 승계하지 않고 재판정한다.

**결정(v0.2)**: **A(로컬)로 MVP를 구현**하고, 인터페이스(`src/stt/engine.py`)를 교체 가능하게 두어 B(클라우드)를 옵션으로 후속 추가한다(FR-11). 근거는 §7.2.1.

#### 7.2.1 확정 스택 (조사 근거: `docs/research_회의록STT_20260819/report.md`)

| 구성요소 | 채택 | 라이선스 | 채택 이유 |
|---|---|---|---|
| 오디오 디코딩 | **PyAV** | BSD 계열 | 휠에 FFmpeg 라이브러리 포함 → m4a/aac를 **별도 ffmpeg 동봉 없이** 처리(F006) |
| 전사 | **faster-whisper** (CTranslate2) | MIT | PyTorch 불필요, CPU int8, **Silero VAD 내장**, 롱폼 지원(F006). 한국어는 Whisper 계열이 우세(F010) |
| 화자 분리 | **sherpa-onnx** offline speaker diarization | Apache-2.0 | 휠 4MB·PyTorch 불필요, **HF 토큰/게이트 불필요**, 화자 수 자동 추정(F001~F004) |
| 결합 | 자체 구현 | — | 타임스탬프 겹침으로 전사 세그먼트 ↔ 화자 매칭 |

**배제 결정과 그 이유**

- `openai/whisper` **원본 배제** — PyTorch 런타임(수 GB)을 데스크톱 앱에 끌고 들어와야 한다. (참고: 사용자가 언급한 "codex 쪽 음성엔진"은 정확히는 OpenAI GitHub의 `openai/whisper`이며, Codex 계열에는 음성 엔진이 없다.)
- **pyannote.audio 직접 사용 배제** — 사실상 표준이지만 모델이 **게이트**되어 있어 사용 조건 수락 + Hugging Face 토큰이 필요하다(F005). 일반 사무 사용자에게 HF 계정 발급을 요구하면 기능이 열리지 않는다. sherpa-onnx가 **같은 pyannote 세그멘테이션 모델의 ONNX 변환본을 GitHub Releases로 무게이트 배포**하므로 이쪽을 쓴다(F003).
- **whisper.cpp 내장 화자분리(tinydiarize) 배제** — 실험적이며 `small.en` 전용(영어)이라 한국어 회의에 쓸 수 없다(F007).
- **모델 동봉 배제** — noScribe가 모델 동봉으로 배포 용량 수 GB가 된 전철(F011)을 피한다. kordoc 런타임 설치 선례를 이식해 첫 사용 시 다운로드한다(FR-09).

**폴백 스택(경량 단일 의존성)**: sherpa-onnx 단독으로 VAD + ASR(SenseVoice 또는 한국어 zipformer) + 화자분리를 모두 처리(F008·F009). 휠 4MB로 끝나지만 한국어 정확도 열위 가능성(F010)과 롱폼 직접 조립 부담이 있다. 파일럿에서 A/B 비교한다.

### 7.3 파이프라인

```
드롭(m4a/mp4/…) → audio.normalize (ffmpeg: wav 16k mono, 오디오 트랙 추출)
   → [길면 audio.chunk]
   → engine.transcribe        (텍스트 + 타임스탬프, ko/en 자동)
   → diarize.assign           (화자 라벨 부여 · 세그먼트 병합)
   → 사용자 검토 · 화자 이름 매핑 (FR-05/06)
   → serialize.to_minutes_input
   → 기존 draft_minutes(...) → 검토 팝업 → build_minutes → HWPX
   → .transcript.json/.txt 사이드카 저장 (FR-08)
```

### 7.4 반드시 손봐야 할 기존 제약 — 첨부 분량 상한

`src/convert/attach.py`의 `MAX_ATTACH_TOTAL = 30_000`(글자)은 **문서 첨부** 기준으로 잡힌 값이다. 회의 전사본은 이 상한과 정면으로 부딪힌다.

- 한국어 발화는 대략 **분당 300~400자** 수준으로 잡아 왔다. 합성음 1차 파일럿(Q6)은 전사 기준 small 273.8자/분, medium 271.1자/분 — **합성음 기준이며 실제 회의 녹음은 미측정**.
- 60분 회의 ≈ 18,000~24,000자 → 문서 상한 근접
- 120분 회의 ≈ 36,000~48,000자 → 문서 상한 초과 → 뒷부분이 통째로 잘림

회의록에서 **회의 후반부(대개 결론·할 일이 나오는 구간)가 잘리는 것**은 치명적이다.

**결정·구현(v0.3)**: Q3의 3안 중 **1안(전사본 전용 상한을 별도로 두고 상향)** 으로 확정했고, `src/convert/attach.py`에 반영되어 있다.

- 문서 첨부 상한 `MAX_ATTACH_TOTAL = 30_000`은 그대로 둔다.
- 전사본 전용 상한 `MAX_TRANSCRIPT_TOTAL = 120_000`을 둔다. 근거: 한국어 보수 환산 1.3자/토큰이면 약 9만 토큰이며, 현재 쓰는 프로바이더(Gemini/OpenAI/Anthropic) 입력 상한이 이보다 훨씬 크다. 2시간 회의(약 48,000자)도 이 상한 안에 들어온다.
- `merge_attachments`는 첨부 항목의 선택적 `kind`(`"document"` | `"transcript"`)로 예산을 나눈다. `kind`가 없으면 문서 상한을 써서 **기존 호출과 동일**하다.
- 전사본이 상한을 넘으면 경고 문구가 "회의 후반부가 잘렸습니다"를 포함한다. 문서 첨부 초과 경고는 종전과 같다.

2안(구간별 요약 후 투입, FR-21)과 3안(맵-리듀스 초안)은 후속 후보로 남긴다. 지금 구현한 것은 1안뿐이다.

### 7.6 신규 의존성 (v0.2 확정, 배포 방침 v0.4)

| 패키지 | 용도 | 비고 |
|---|---|---|
| `av` (PyAV) | m4a/mp4 등 디코딩 → 16kHz mono | FFmpeg 별도 동봉 불필요 |
| `faster-whisper` (+`ctranslate2`) | 전사 | 모델은 런타임 다운로드 |
| `sherpa-onnx` | 화자 분리 | 휠 4MB, 모델은 GitHub Releases |
| `numpy` | 오디오 배열 | 위 패키지들의 공통 전제 |

`requirements.txt`에 **선택 설치**로 적혀 있다. 미설치여도 앱 부팅·견적서·회의록·영수증은 정상이다. STT만 비활성.

**배포 방식 (확정)**: STT 엔진 패키지(`av`, `faster_whisper`, `ctranslate2`, `sherpa_onnx`, `onnxruntime`, `tokenizers`, `huggingface_hub` 등)는 **exe에 동봉하지 않는다.** `navion_quote.spec`의 `excludes`가 이 목록을 빼고, 우리 코드 모듈만 `hiddenimports`에 넣는다 (`src.stt`, `src.stt.audio`/`engine`/`diarize`/`runtime`/`serialize`, `src.api.stt`). 지연 import라 정적 분석이 모듈을 놓칠 수 있기 때문이다.

근거:

- 파일럿 Q9(합성음 체인, `docs/research_회의록STT_20260819/pilot_result.md`): small 스택 1,359.3 MB, medium 스택 3,448.0 MB. 모델 동봉은 이 숫자로 기각.
- 이 워크트리 onedir 실측(`dist/`, 2026-08-20): 엔진 제외 **304.2 MB**. 엔진을 넣은 빌드는 돌리지 않았다(미측정). small 스택을 통째로 붙이면 배포가 GB 단위로 커진다.

사용자는 STT를 쓰려면 엔진을 선택 설치한다. 가중치(화자분리 onnx, faster-whisper CT2)는 기존대로 최초 사용 시 내려받는다(`src/stt/runtime.py`, HuggingFace 캐시).

## 8. 성공 지표

### 8.1 파일럿 게이트 (착수 판정)

내비온 **실제 회의 녹음**으로 측정한다. 공개 벤치마크 수치는 게이트 기준으로 쓰지 않는다. 통과 판정에는 **실제 회의 녹음 3~5건**(한국어 위주 + 한영 혼용 포함)이 필요하다.

1차 파일럿(2026-08-19, `docs/research_회의록STT_20260819/pilot_result.md`)은 Windows SAPI **합성음** 1건(5.80분, 한국어 음성 Heami 1명 + 피치·속도만 다른 2화자)으로 수행했다. **게이트를 통과시키지 않았다.**

- **전사 가독성**: 사람이 읽고 회의 내용을 복원할 수 있는가(정성 판정). 고유명사 오인식은 감점하되, 사업명·기관명은 FR-20 용어사전으로 보완 가능하므로 치명 결함으로 보지 않는다. 합성음에서는 줄거리·숫자·날짜는 복원 가능했으나 약어·기관명은 자주 붕괴했다.
- **화자 분리 유용성**: 실제 화자 수 대비 추정 화자 수의 오차, 발언 귀속이 사용자 수정 몇 회로 정리되는가. 1차 파일럿은 **동일 성문 TTS**라 화자분리를 판정할 수 없다(검증 불가 — "실패"가 아님). 실제 2인 녹음이 필요하다.
- **처리 시간**: 합성음 실측은 오디오 1분당 small 35.5초, medium 58.6초(i7-13700K, CPU int8). 60분 환산은 약 35분 / 약 59분이며, **60분 실파일은 미측정**. 실제 녹음으로 상한을 정한다.
- **한영 혼용**: 영어 기술 용어·문장이 통째로 누락되거나 엉뚱한 한국어로 치환되지 않는가. 합성 TTS가 영어를 한국어 음소로 읽어 1차 시험이 왜곡됐다. **미해소.**

코드 스택(`faster-whisper` + `sherpa-onnx`, 모델 런타임 다운로드)은 **후보로 유지**한다. 기본 모델은 속도 때문에 **small을 실사용 후보**로 두고, 실제 녹음에서 medium의 고유명사 이득이 확인되면 그때 올린다.

게이트 미달 시: 엔진 교체(§7.2 다른 안) 또는 기능 보류. 부정확한 전사를 회의록 초안에 넣는 것은 "정확성 우선" 원칙 위반이다.

### 8.2 사업

- 회의 종료 → 회의록 초안 완성까지 소요 시간 단축.
- 외부 STT 앱 사용 중단(왕복 제거).

### 8.3 기술

- 전사 실패율(재시도 후에도 실패) 상한 관리.
- 긴 파일(2시간+) 처리 시 크래시·메모리 초과 0건.
- 엔진 설치 성공률(사용자 PC 환경 다양성).

## 11. 사용자 스토리

### US-001. 녹음 파일 드롭
- 설명: 사용자로서, 회의 녹음(m4a)을 회의록 첨부 드롭존에 그대로 드롭하고 싶다.
- 수용 기준:
  - 지원 음성/영상 확장자를 드롭하면 접수되고 STT 경로로 라우팅된다.
  - 문서 첨부와 음성 첨부를 함께 올려도 각각 올바른 경로로 처리된다.
  - 미지원 형식은 사유와 함께 목록에서 제외 표시된다.

### US-002. 한국어·영어 혼용 전사
- 설명: 사용자로서, 한국어 회의 중 섞인 영어 용어·문장이 그대로 받아쓰기되길 원한다.
- 수용 기준:
  - 한국어 구간과 영어 구간이 모두 텍스트로 남는다.
  - 영어 구간이 누락되거나 무관한 한국어로 치환되지 않는다.
  - 언어 자동 감지가 실패할 경우 사용자가 주 언어를 지정할 수 있다.

### US-003. 화자 분리
- 설명: 사용자로서, 누가 말했는지 구분된 전사본을 원한다.
- 수용 기준:
  - 각 발화 세그먼트에 화자 라벨과 시작·종료 시각이 붙는다.
  - 화자 수를 사전에 몰라도 자동 추정된다.
  - 동일 화자의 연속 발화는 하나로 병합되어 읽기 쉽다.

### US-004. 화자 이름 지정
- 설명: 사용자로서, `화자1`에 실명·소속을 붙여 회의록에 반영하고 싶다.
- 수용 기준:
  - 검토 화면에서 화자별 이름을 입력하면 전사본 전체에 즉시 반영된다.
  - 지정한 이름이 회의록 초안의 `participants`에 반영된다.
  - 이름을 지정하지 않은 화자는 `화자N`으로 유지되며 임의 추측되지 않는다.

### US-005. 진행 상황 확인과 취소
- 설명: 사용자로서, 긴 녹음을 처리하는 동안 진행 상황을 보고 필요하면 취소하고 싶다.
- 수용 기준:
  - 단계와 진행률(또는 처리된 재생시간)이 표시된다.
  - 취소 버튼이 즉시 반응하고 임시 파일이 정리된다.
  - 처리 중에도 앱의 다른 기능이 멎지 않는다.

### US-006. 전사본 검토·수정
- 설명: 사용자로서, 잘못 받아쓴 부분을 그 자리에서 고치고 싶다.
- 수용 기준:
  - 타임라인 형태로 세그먼트가 표시되고 인라인 편집이 가능하다.
  - 저신뢰 구간이 시각적으로 강조된다.
  - 수정 내용이 회의록 초안 생성에 반영된다.

### US-007. 전사본으로 회의록 초안 생성
- 설명: 사용자로서, 확인한 전사본을 그대로 회의록 초안 생성에 넘기고 싶다.
- 수용 기준:
  - 버튼 한 번으로 기존 회의록 AI 초안 흐름으로 이어진다.
  - 회의 후반부가 분량 상한으로 잘리지 않는다.
  - 이후 검토 팝업·HWPX 생성 흐름은 기존과 동일하게 동작한다.

### US-008. 전사 원문 보존
- 설명: 사용자로서, 나중에 회의록 내용을 원본과 대조할 수 있도록 전사본이 저장되길 원한다.
- 수용 기준:
  - `.transcript.json`과 사람이 읽는 `.txt`가 회의록 산출물 옆에 저장된다.
  - 저장 실패는 경고로 처리되고 회의록 생성 자체를 막지 않는다(기존 사이드카 규약과 동일).

### US-009. 엔진 설치 안내
- 설명: 사용자로서, 음성 기능을 처음 쓸 때 무엇을 설치해야 하는지 안내받고 필요한 것을 1클릭으로 받고 싶다.
- 수용 기준:
  - 엔진/모델 미준비 시 한국어 안내 배너가 표시된다.
  - 설치 진행률이 표시되고, 실패 시 사유가 한국어로 안내된다.
  - 설치 후 대기 중이던 파일이 이어서 처리된다.

### US-010. 부분 실패 처리
- 설명: 사용자로서, 여러 파일 중 하나가 실패해도 나머지는 처리되길 원한다.
- 수용 기준:
  - 실패 파일이 사유와 함께 구분 표시된다.
  - 개별 재시도가 가능하다.
  - 한 파일의 실패가 전체를 중단시키지 않는다.

### US-011. 긴 회의 처리
- 설명: 사용자로서, 2시간짜리 회의 녹음도 실패 없이 처리되길 원한다.
- 수용 기준:
  - 장시간 파일이 자동 분할 처리되어 완주한다.
  - 메모리 초과·타임아웃으로 앱이 종료되지 않는다.
  - 처리 시간이 사전에 안내된다.

### US-012. 외부 전송 고지 (보안 접근)
- 설명: 사용자로서, 녹음이 외부로 전송되는지 여부를 명확히 알고 선택하고 싶다.
- 수용 기준:
  - 클라우드 모드 사용 시 최초 1회 외부 전송 고지가 표시된다.
  - 현재 처리 모드(로컬/클라우드)가 화면에서 항상 확인 가능하다.
  - 로컬 모드는 네트워크 없이 동작한다.

### US-013. 임시 파일 정리 (보안 접근)
- 설명: 사용자로서, 변환 과정에서 만들어진 오디오 사본이 PC에 남지 않길 원한다.
- 수용 기준:
  - 처리 완료·취소·실패 어느 경우에도 임시 오디오가 삭제된다.
  - 사용자가 명시적으로 저장한 전사본만 작업 폴더에 남는다.

### US-014. 화자 정보의 목적 제한 (보안 접근)
- 설명: 사용자로서, 화자 구분이 세션 내부에만 쓰이고 목소리가 등록·저장되지 않길 원한다.
- 수용 기준:
  - 성문·화자 임베딩이 회의 간 재사용을 위해 영구 저장되지 않는다.
  - 화자 이름 매핑은 해당 회의 전사본에만 귀속된다.

## 12. 부록: 다음 단계 (v0.4 기준)

GitHub 탐색은 완료했다(`docs/research_회의록STT_20260819/report.md`). 1차 파일럿은 **합성음으로 수행했고 게이트를 통과시키지 않았다**(`docs/research_회의록STT_20260819/pilot_result.md`). 통과 판정에는 **실제 회의 녹음 3~5건**이 필요하다. 실제 녹음 없이 남은 Q5~Q7을 풀 수 없고, 정확도 미달 상태로 회의록에 투입하는 것은 "정확성 우선" 원칙 위반이다.

코드 스택(`faster-whisper` + `sherpa-onnx`, 모델 런타임 다운로드)은 후보로 유지한다. 기본 모델은 속도 때문에 **small을 실사용 후보**로 두고, 실제 녹음에서 medium의 고유명사 이득이 확인되면 그때 올린다.

### 12.1 파일럿 프로토타입

독립 스크립트 `scripts/stt_pilot.py` / `scripts/stt_selftest.py`로 1차(합성음)를 돌렸다. 2차는 같은 체인에 **실제 회의 녹음 m4a 3~5건**을 넣는다.

```
scripts/stt_pilot.py   (앱 코드 아님)
  입력: 실제 회의 녹음 m4a 3~5건
  처리: PyAV 디코딩 → faster-whisper 전사 → sherpa-onnx 화자분리 → 결합 출력
  출력: [mm:ss] 화자N: 텍스트  +  처리 시간·글자 수 통계
```

측정 항목 = §8.1 게이트 + Q5(한영 혼용, 실제 발화) + Q6(분당 글자 수, 실제 녹음) + Q7(60분 실파일 또는 그에 준하는 실측) + 화자분리(실제 2인 이상 성문).

### 12.2 착수 순서

1. `MAX_ATTACH_TOTAL` 분리(§7.4) — **완료**. `MAX_TRANSCRIPT_TOTAL = 120_000` (`src/convert/attach.py`).
2. `src/stt/` 구현 (engine → audio → diarize → serialize → runtime) — **완료**. 다섯 모듈이 `src/stt/`에 있다.
3. `src/api/stt.py` + UI 분기(드롭존 라우팅·진행률·전사 검토 화면) — **완료**. `SttApi`가 `Api` 상속 목록에 있고, `ui/index.html`에 `#mn-stt-banner` / `#mn-stt-review`가 있다.
4. 배포 spec 엔진 미동봉(`navion_quote.spec` `excludes` / STT `hiddenimports`) — **완료**.
5. 합성음 1차 파일럿 — **수행, 게이트 미통과**. 실제 회의 녹음 3~5건이 남음.
6. 화자 이름 매핑 → `participants` 연결(FR-06).
7. 전사본 사이드카 저장(FR-08).
