# 회의록 노트(회의 기록 관리) 기능 PRD

문서 성격: 내비온 견적서 생성기 **회의록 기능의 경험 계층 확장**을 위한 제품 요구사항 정의서(내부용).

작성 근거: 현행 코드 실측(`src/api/minutes.py` 473줄, `src/minutes/hwpx_minutes.py` 550줄, `src/ai/minutes.py`, `src/store/minutes_store.py`, `src/scan/hwpx_scan.py`, 영수증 기능 선례 `src/api/receipt.py`) + `docs/PRD_회의록STT.md` v0.3 + 네이버 클로바노트 관찰 + GitHub 탐색 결과(`docs/research_회의록노트_20260819/report.md`).

**v0.2 갱신(2026-08-19)**: 조사 보고서 4장에 따라 §7.2 검색·§7.3 오디오 전달·§7.4 청킹 목적을 확정하고, Q2·Q6을 해소했다. Q1(오디오 보관)은 오픈소스 선례가 없어 존치한다.

### 1.2 제품 요약

회의 녹음을 넣으면 앱이 **받아쓰고, 누가 말했는지 나누고, 무슨 이야기였는지 요약하고, 무엇을 하기로 했는지 뽑아내어**, 그 회의를 **노트로 앱에 남긴다**. 사용자는 나중에 그 노트를 검색해 찾고, 궁금한 대목은 **그 지점의 음성을 바로 들어** 확인하고, 확정되면 지금과 똑같이 한글(HWPX) 회의록을 만든다.

한 줄 요약: **"회의록을 '한 번 만들고 끝나는 파일'에서 '쌓이고 찾아지는 기록'으로 바꾼다."**

### 1.3 배경 — 왜 노트 계층이 필요한가

현재 회의록 기능은 **문서 한 장을 만들어 내보내면 끝난다.** 메모를 쓰거나 파일을 첨부하면 AI가 초안을 만들고, 사용자 양식에 채워 HWPX로 저장한다. 회의의 흔적은 `.hwpx`와 재편집용 `.minutes.json` 두 개뿐이다.

이 구조에서 실제로 발생하는 손실:

- **근거가 사라진다.** 완성된 회의록에는 결론만 남고, "그 숫자가 어디서 나왔더라"를 확인할 원본이 없다. 녹음은 개인 폰에, 메모는 각자 노트에 흩어진다.
- **찾을 수가 없다.** "작년에 KIST와 라이다 단가 이야기한 게 몇 차 회의였지"를 알아내려면 폴더를 열어 파일을 하나씩 열어봐야 한다. 현행 `scan_minutes_folder`는 파일명·표지 정보 수준의 카드만 만든다.
- **후속 조치가 문서 밖으로 새어 나간다.** 회의에서 정한 담당자와 기한은 회의록 본문에 문장으로만 남고, 별도로 관리되지 않는다.
- **AI 초안의 재료가 빈약하다.** 사용자가 손으로 요약한 메모를 입력으로 받으므로, 이미 사람이 한 번 압축한 정보 위에서 다시 요약한다. 전사본 전체를 재료로 쓰면 초안 품질이 근본적으로 달라진다.

클로바노트가 푼 문제가 정확히 이것이다. 이 PRD는 같은 문제를 **우리 앱의 산출물(HWPX 회의록)로 이어지는 형태**로 푼다.

### 1.4 기존 자산과의 경계 — 이 문서가 다루지 않는 것

회의록 기능은 세 계층으로 나뉜다. 이 PRD는 가운데 계층만 다룬다.

| 계층 | 정의 문서 | 다루는 범위 | 상태 |
|---|---|---|---|
| 입력(엔진) | `PRD_회의록STT.md` | 오디오 → 전사 세그먼트 + 화자 라벨 + 타임스탬프 | PRD v0.2, 파일럿 대기 |
| **경험(본 문서)** | **이 PRD** | **전사본·메모 → 요약·키워드·액션아이템, 노트 축적·검색·재생·북마크** | **신규** |
| 산출(구현 완료) | 코드 | `MINUTES_SCHEMA` → 사용자 한글 양식에 채워 HWPX 생성 | 운영 중 |

**중복 금지 원칙**: 전사 엔진 선정·화자 분리 알고리즘·오디오 디코딩은 전부 선행 문서 소관이다. 이 문서는 "전사 세그먼트 배열이 주어졌다"를 전제로 시작한다.

**독립 착수 가능 범위(중요)**: 노트 계층의 상당 부분은 STT 파일럿 게이트와 **무관하게** 착수할 수 있다. 요약·키워드·액션아이템·노트 목록·검색은 입력이 오디오가 아니라 **텍스트(붙여넣은 전사본, 첨부 문서, 손메모)** 여도 그대로 동작한다. STT가 늦어져도 이 기능의 절반 이상은 먼저 사용자 손에 갈 수 있다. 착수 순서(§12)는 이 점을 이용한다.

## 2. 목표와 비목표

### 2.1 사업 목표

- 회의 1건을 정리하는 **총 소요 시간**을 현재의 절반 이하로 줄인다(외부 STT 앱 왕복 + 손요약 + 양식 채우기 → 앱 안 한 번).
- 회의록 품질의 **하한을 올린다**. 사람이 요약을 건너뛰어도 전사본 기반 초안이 나오므로 "회의록을 못 쓴 회의"가 사라진다.
- 과거 회의가 **자산으로 축적된다**. 제안서·정산·기술이전 협의에서 과거 합의사항을 근거와 함께 즉시 꺼낼 수 있다.

### 2.2 사용자 목표

- 녹음을 넣고 다른 일을 하다 돌아오면 정리가 끝나 있다.
- 요약을 믿어도 되는지 **그 자리에서 근거를 확인**할 수 있다(해당 발언 구간 재생·원문 대조).
- "누가 무엇을 언제까지"가 목록으로 뽑혀 나온다.
- 지난 회의를 **한 번의 검색으로** 찾는다.

### 2.3 비목표 (Non-goals)

- **회의 일정 관리·캘린더 연동** — 회의를 잡는 일은 다루지 않는다. 끝난 회의의 기록만 다룬다.
- **다중 사용자 동시 편집·서버 동기화** — 로컬 데스크톱 앱이다. 노트는 사용자 PC의 작업 폴더에 파일로 남는다. 공유는 파일·텍스트 내보내기로 한다.
- **화자 성문 등록·영구 재식별(speaker ID DB)** — 선행 문서의 비목표를 그대로 승계한다. 화자 이름은 회의마다 사용자가 붙인다. (§9 R-05)
- **완전 무인 자동 확정** — 요약·액션아이템을 사용자 확인 없이 회의록으로 확정하지 않는다. 기존 "AI 초안 → 검토 → 확정" 게이트를 유지한다.
- **할 일 관리 제품화** — 액션아이템은 추출·표시·내보내기까지다. 진행 상태 추적·알림·담당자 배정 워크플로는 만들지 않는다.
- **음성 편집·잡음 제거** — 오디오는 재생만 한다.

## 3. 사용자와 권한

### 3.1 페르소나

| 페르소나 | 상황 | 이 기능에서 얻는 것 |
|---|---|---|
| 회의록 담당 실무자 | 주 2~5회 외부 협의, 매번 녹음 후 손정리 | 정리 시간 단축이 가장 큰 이득. 주 사용자 |
| 회의 참석 연구원 | 회의록은 안 쓰지만 결론은 알아야 함 | 요약·액션아이템만 확인. 읽기 중심 |
| 과제 책임자 | 몇 달 전 합의사항을 근거와 함께 확인해야 함 | 검색·재생이 핵심. 간헐적 사용 |

### 3.2 접근·권한 모델

- 노트는 **사용자 PC의 작업 폴더**에 파일로 존재한다. 앱은 별도 계정·권한 계층을 만들지 않는다. 폴더 접근 권한이 곧 노트 접근 권한이다.
- **외부 전송 고지**: AI 요약은 LLM 프로바이더로 전사본을 전송한다. 회의 내용이 외부로 나가는 행위이므로, 요약 실행 전 대상 프로바이더명과 전송 분량을 고지하고 사용자 동의를 받는다(영수증 기능의 `mark_receipt_notice_seen` 선례 이식).
- **오디오 원본**은 회의 참석자의 음성이다. 보관 정책은 §10 Q1에서 결정한다.

## 5. 사용자 경험(UX) 흐름

### 5.1 진입점

기존 회의록 탭을 유지한다. 신규 문서 유형을 만들지 않는다. 탭 내부가 **[새 회의] / [노트 목록]** 두 모드로 나뉜다.

```
 └───────────────────────────────────────────────────────┘
```


검색 결과는 노트 단위가 아니라 **매칭 구간 단위**로 보여준다. 문장을 누르면 그 회의의 그 지점으로 바로 들어간다.

### 5.4 상태·예외 경험

- **요약 중**: 단계 표시(전사본 준비 → 요약 요청 → 정리)와 취소. 요약은 LLM 왕복이므로 수십 초가 걸릴 수 있다.
- **요약 실패**: 전사본은 이미 저장되어 있음을 명확히 알리고 "요약만 다시 시도" 버튼을 제공한다. 실패로 회의 자체를 잃었다는 인상을 주지 않는다.
- **오디오 없음**: 텍스트만으로 만든 노트는 재생·타임스탬프 UI를 감춘다. 근거 점프는 전사본 위치 이동으로 대체한다.
- **긴 회의**: 전사본이 LLM 입력 상한을 넘으면 구간 분할 요약 후 병합한다(§7.4).
- **외부 전송 고지 미동의**: 요약 없이 전사본만 보관하는 상태로 노트를 완성할 수 있어야 한다. 기능이 통째로 잠기면 안 된다.

## 6. 데이터 정의

### 6.1 저장 구조 — 기존 사이드카 규약의 확장

신규 데이터베이스를 도입하지 않는다. 회의록 폴더에 **같은 basename의 형제 파일**로 둔다. 현행 `.minutes.json` 사이드카 규약과 `scan_minutes_folder`의 스캔 방식을 그대로 승계한다.

```
<작업폴더>/
  2026-08-19_기술이전협의3차.hwpx             ← 최종 산출물         (기존)
  2026-08-19_기술이전협의3차.minutes.json     ← 회의록 재편집 데이터 (기존)
  2026-08-19_기술이전협의3차.transcript.json  ← 전사 세그먼트       (선행 문서)
  2026-08-19_기술이전협의3차.note.json        ← 요약·화자·북마크    (신규, 본 문서)
  2026-08-19_기술이전협의3차.m4a              ← 원본 오디오 (보관 시)
```

이 선택의 이유:

- **파일이 진실의 원천이다.** 사용자가 폴더째 복사·백업·이동해도 노트가 통째로 따라간다. 별도 DB를 두면 파일과 DB가 어긋나는 순간 사용자는 어느 쪽을 믿어야 할지 알 수 없다.
- 기존 갤러리(`scan_minutes_folder`)가 **이미 고아 사이드카를 카드로 만드는 로직**을 갖고 있어 재사용된다.
- `.hwpx`가 아직 없는 상태(회의는 했지만 회의록은 안 만듦)도 노트로 성립한다.

검색 인덱스는 **파생물**이다. 앱 데이터 폴더에 두고, 폴더 스캔으로 언제든 재생성한다. 인덱스가 깨져도 데이터는 잃지 않는다.

### 6.2 노트 스키마 (`.note.json`, 가안)

```jsonc
{
  "schema": 1,
  "title": "기술이전 협의 3차",
  "created_at": "2026-08-19T14:32:01",
  "duration_sec": 3721,
  "source": {
    "kind": "audio",              // audio | text
    "audio_path": "2026-08-19_기술이전협의3차.m4a",   // 노트 파일 기준 상대경로
    "audio_kept": true            // false면 재생 UI 비활성
  },
  "speakers": [
    { "key": "화자1", "name": "김형일", "org": "내비온" },
    { "key": "화자2", "name": "김종민", "org": "KIST" }
  ],
  "summary": { /* §6.3 */ },
  "summary_meta": {
    "provider": "gemini", "model": "...",
    "generated_at": "2026-08-19T15:40:11",
    "edited_by_user": true,       // 사용자가 손댔으면 재요약 시 확인
    "chunked": false              // 구간 분할 요약 여부
  },
  "bookmarks": [
    { "id": "b1", "t_ms": 512000, "seg_id": 142, "memo": "단가 근거 재확인" }
  ],
  "tags": ["기술이전", "KIST"],
  "links": {
    "transcript": "2026-08-19_기술이전협의3차.transcript.json",
    "minutes_json": "2026-08-19_기술이전협의3차.minutes.json",
    "hwpx": "2026-08-19_기술이전협의3차.hwpx"
  }
}
```

### 6.3 요약 스키마 (`NOTE_SUMMARY_SCHEMA` — LLM 구조화 출력)

`src/ai/minutes.py`의 `MINUTES_SCHEMA` 선례를 그대로 따라 `complete_json(schema=...)` 경유로 받는다.

| 필드 | 형 | 설명 |
|---|---|---|
| `one_liner` | STRING | 회의 전체를 한 문장으로 |
| `topics[]` | ARRAY | `{title, t_ms, points[]}` — 주제 제목, 시작 시각, 요지 2~5개 |
| `keywords[]` | ARRAY(STRING) | 핵심어 5~15개 |
| `decisions[]` | ARRAY | `{text, t_ms}` — 확정된 사항과 근거 시각 |
| `action_items[]` | ARRAY | `{task, owner, due, t_ms}` — 언급 없으면 `owner`·`due`는 빈 문자열 |
| `open_issues[]` | ARRAY | `{text, t_ms}` — 결론 없이 넘어간 안건 |

**모든 항목에 `t_ms`(근거 시각)를 필수로 요구한다.** 이것이 요약 환각을 잡는 유일한 실효적 장치다. 근거 시각이 없는 항목은 화면에서 "근거 미확인"으로 표시해 사용자가 의심하게 만든다(R-01).

**추측 금지 규칙**을 프롬프트에 명시한다: 담당자·기한·금액은 발언에 나온 것만 채우고, 문맥상 그럴듯한 값을 지어내지 않는다. 영수증 기능이 미확인 값을 `null`로 두고 검증 플래그를 띄우는 것과 같은 원칙이다.

### 6.4 회의록 초안 입력 포맷 (NR-08)

기존 `minutes_draft`는 `description` 문자열 하나를 받는다. 요약 결과를 **사람이 읽는 텍스트로 직렬화**해 그 자리에 넣는다. 새 엔드포인트를 만들지 않는다.

```
[회의 요약]
라이다 단가와 기술료 배분 합의, 계약 초안은 9월 첫 주 송부

[참석자]
내비온 김형일 / KIST 김종민

[주제별 논의]
■ 단가 협의 (04:12)
  - 양산 기준 단가 18만원 선에서 접점
  - 초도 물량 500대 조건부

[결정사항]
- 초도 500대 조건부 단가 18만원 (09:03)

[할 일]
- 계약 초안 송부 — 김형일 — 9/4 (55:18)
```

이 포맷은 전사본 원문(수만 자)의 **1/20 이하**로 줄어들어 첨부 분량 상한 문제를 구조적으로 없앤다.

## 7. 기술 설계 개요

### 7.1 모듈 골격 — 영수증·회의록 선례 동형

```
src/note/
  __init__.py
  store.py        # .note.json 읽기·쓰기·마이그레이션 (minutes_store 선례)
  summarize.py    # 전사본 → NOTE_SUMMARY_SCHEMA (청크 분할·병합 포함)
  serialize.py    # 요약 → minutes_draft 입력 텍스트 (§6.4)
  search.py       # 인덱스 구축·질의
src/ai/
  note.py         # NOTE_SUMMARY_SCHEMA · 프롬프트 · 정규화 (ai/minutes.py 동형)
src/api/
  note.py         # js_api 엔드포인트 (api/receipt.py 동형)
```

`src/api/minutes.py`(473줄)는 이미 크다. 노트 엔드포인트를 여기에 더하지 않고 `src/api/note.py`로 분리한다 — 영수증이 `src/api/receipt.py`로 분리된 선례와 동일.

### 7.2 검색 — 표준 라이브러리로 끝낸다

**sqlite3 FTS5**를 쓴다. `sqlite3`는 파이썬 표준 라이브러리이고 FTS5는 Windows 공식 빌드에 포함되어 있어 **신규 의존성이 0이다**. 검색 엔진 라이브러리를 추가할 이유가 없다.

- 인덱스 위치: 앱 데이터 폴더(`%LOCALAPPDATA%`). 작업 폴더를 오염시키지 않는다.
- 색인 대상: 제목 · 날짜 · 참석자 · 키워드 · 요약 전문 · 전사본 전문
- 갱신: 폴더 스캔 시 파일 `mtime` 비교로 변경분만 재색인(NR-27)
- 한국어 토크나이징: **FTS5 `trigram`으로 확정**. 기본 `unicode61`은 한국어를 공백 단위로만 잘라 "단가를"로 색인되면 "단가" 검색이 빗나간다. trigram은 글자 3개 단위라 부분일치가 된다(조사: 3 유니코드 문자 미만 부분열은 매치되지 않음).
  - **2글자 이하 질의는 `LIKE '%…%'` 폴백**. trigram 인덱스가 LIKE도 가속한다(로컬 실측 L3).
  - **`detail=none` 사용 금지**. 이 옵션은 `highlight()`/`snippet()`을 깨뜨려 검색 결과 문맥(§5.3)이 나오지 않는다.

### 7.3 오디오 재생 — 네이티브 `<audio>` 우선

플레이어 라이브러리를 넣지 않는다. WebView2는 Chromium이므로 HTML5 `<audio>`가 m4a/mp3/wav를 그대로 재생한다. 배속·구간이동도 표준 API(`playbackRate`, `currentTime`)로 끝난다.

**오디오 전달 — 자체 bottle 라우트로 확정**(조사 M6, 로컬 실측).

| 방식 | 판정 | 이유 |
|---|---|---|
| `file:///` 직접 참조 | **배제** | pywebview 메인테이너가 "file:// protocol is flawed"로 명시. 공식 문서도 사용 비권장 |
| base64 data URI | **배제** | 60분 m4a ≈ 60MB → base64 80MB를 js_api로 넘김. 비현실적 |
| 내장 `http_server=True` | **배제** | `os.path.commonpath`로 루트를 잡는다. 앱(C 드라이브)과 작업 폴더(다른 드라이브)가 갈리면 `ValueError`로 깨진다(실측) |
| **자체 bottle 라우트** | **채택** | bottle은 pywebview의 기존 의존성. `static_file`이 Range/206을 지원하고, `root`를 요청마다 지정할 수 있다 |

구현 위치는 `src/note/serve.py`(신규). 클라이언트는 절대경로를 모르고 `/audio/<note_id>`만 본다. **파일럿은 `file://` 재생이 아니라 bottle 라우트의 206 Partial Content 응답을 검증한다.**

### 7.4 긴 회의의 요약 — 구간 분할 후 병합

60분 회의 전사본은 대략 3만~5만 자로 추정된다([확인 필요] Q3 — 선행 문서 Q6과 동일 항목이므로 파일럿에서 함께 실측). 보수적 환산(1.3자/토큰)이면 **약 2.3만~3.9만 토큰**이다. 현재 쓰는 주요 모델 입력 상한은 100만 토큰대라 **상한 초과는 현실적으로 발생하지 않는다**(조사 M2).

청킹의 목적은 **"LLM 입력 상한 초과 방어"가 아니다.** 다음을 위한 **로컬 모델 호환성 + lost-in-the-middle 완화** 안전장치다.

1. 전사본을 **화자 전환과 무음 구간을 경계로** N개 구간으로 나눈다(문장 중간을 자르지 않는다)
2. 구간별로 부분 요약을 받는다
3. 부분 요약들을 다시 입력으로 넣어 최종 `NOTE_SUMMARY_SCHEMA`를 만든다
4. `summary_meta.chunked = true`로 표시하고 화면에 "구간 분할 요약" 배지를 단다 — 정보 손실 가능성을 사용자가 알아야 한다

### 7.5 재사용 자산

| 자산 | 위치 | 재사용 방식 |
|---|---|---|
| 멀티 프로바이더 LLM 구조화 출력 | `src/ai/llm.py` `complete_json` | 스키마만 갈아끼우면 그대로 동작 |
| 회의록 사이드카 저장·마이그레이션 | `src/store/minutes_store.py` | `.note.json` 저장에 동형 이식 |
| 폴더 스캔·카드화 | `src/api/minutes.py` `scan_minutes_folder` | 노트 목록으로 확장 |
| 외부 전송 고지 배너 | `src/api/receipt.py` `mark_receipt_notice_seen` | 요약 전 고지에 이식 |
| 드롭존 | `ui` `#minutes-dropzone` | 그대로 사용 |
| HWPX 생성 | `src/minutes/hwpx_minutes.py` | 손대지 않는다 |

### 7.6 신규 의존성

| 기능 | 의존성 | 비고 |
|---|---|---|
| 검색 | **없음** | 표준 `sqlite3` + FTS5 |
| 재생 | **없음** | HTML5 `<audio>` |
| 요약 | **없음** | 기존 `requests` 기반 LLM 경로 |
| 앱 내 녹음(NR-30, P2) | `sounddevice` 등 | Phase 3에서만. 착수 여부는 Q4 |

**Phase 1·2는 신규 파이썬 의존성 없이 구현 가능하다.** 배포 용량이 늘지 않는다.

## 8. 성공 지표

### 8.1 사업

- 회의 1건 정리 소요 시간: 현행 대비 **50% 이상 단축**(사용자 5건 표본 측정)
- 회의록 작성률: 회의 대비 회의록 산출 비율 상승
- 3개월 후 노트 누적 20건 이상 — 축적이 안 되면 검색 기능은 무의미하다

### 8.2 품질

- **액션아이템 정확도**: 사람이 뽑은 목록과 대조해 **재현율 80% 이상, 오탐(없는 할 일 생성) 5% 이하**. 오탐이 재현율보다 중요하다 — 없는 약속이 회의록에 실리면 신뢰가 무너진다
- **근거 시각 정합**: 요약 항목의 `t_ms`가 실제 해당 발언 구간과 일치하는 비율 90% 이상
- 요약 후 사용자 수정률: 문장 단위 30% 이하

### 8.3 기술

- 60분 전사본 요약 소요: **60초 이내**
- 노트 1,000건에서 검색 응답: **300ms 이내**
- 재생 싱크 오차: **±0.5초 이내**

## 11. 사용자 스토리

### NS-001. 녹음에서 요약까지 한 번에
회의록 담당자로서, 녹음 파일을 넣고 자리를 비웠다 돌아오면 요약과 할 일이 정리되어 있기를 바란다.
**인수 조건**: 파일 투입 후 추가 조작 없이 전사 → 화자 분리 → 요약이 이어진다. 각 단계 진행 상황이 보이고 취소할 수 있다.

### NS-002. 요약을 의심할 수 있어야 한다
연구원으로서, 요약에 적힌 내용이 실제로 나온 말인지 그 자리에서 확인하고 싶다.
**인수 조건**: 요약 항목을 누르면 전사본의 근거 구간으로 이동해 하이라이트된다. 오디오가 있으면 그 지점부터 재생된다. 근거 시각이 없는 항목은 시각적으로 구분된다.

### NS-003. 없는 약속이 생기지 않는다
회의록 담당자로서, 담당자나 기한이 회의에서 언급되지 않았다면 빈칸으로 남기를 바란다.
**인수 조건**: `owner`·`due`가 발언에 없으면 빈 문자열로 나오고 화면에 "미지정"으로 표시된다. AI가 그럴듯한 이름·날짜를 채우지 않는다.

### NS-004. 지난 회의를 찾는다
과제 책임자로서, "라이다 단가"로 검색해 관련 회의를 찾고 그 대목을 듣고 싶다.
**인수 조건**: 검색 결과가 매칭 구간 단위로 나오고, 결과를 누르면 해당 노트의 해당 시각으로 진입한다. 1,000건 기준 300ms 이내.

### NS-005. 요약을 고치면 회의록에 반영된다
회의록 담당자로서, AI 요약의 표현을 다듬은 뒤 그대로 회의록을 만들고 싶다.
**인수 조건**: 노트에서 수정한 내용이 `.note.json`에 저장되고, 회의록 초안 생성 시 수정본이 입력된다. 재요약 시 사용자 편집분 덮어쓰기 전 확인한다.

### NS-006. 요약이 실패해도 회의를 잃지 않는다
사용자로서, LLM 오류가 나도 전사본은 남아 있기를 바란다.
**인수 조건**: 요약 실패 시 전사본과 노트는 이미 저장된 상태이고 "요약만 다시 시도" 버튼이 제공된다.

### NS-007. 회의 내용이 어디로 가는지 안다
보안 담당자로서, 회의 전문이 외부로 전송되기 전에 고지받기를 바란다.
**인수 조건**: 첫 요약 실행 전 프로바이더명과 전송 분량을 고지하고 동의를 받는다. 미동의 시 전사·노트 보관은 정상 동작하고 요약만 비활성화된다.

### NS-008. 오디오 보관을 통제한다
사용자로서, 참석자 음성이 내 PC 어디에 남는지 알고 지울 수 있기를 바란다.
**인수 조건**: 오디오 보관 여부가 노트 화면에 표시되고, 노트 삭제 시 오디오도 함께 지워진다. 설정에서 보관을 끌 수 있다.

### NS-009. 텍스트만으로도 노트가 된다
사용자로서, 녹음이 없는 회의도 메모를 붙여 노트로 남기고 싶다.
**인수 조건**: 오디오 없이 텍스트 입력만으로 요약·액션아이템·검색이 동작한다. 재생 UI는 감춰진다.

### NS-010. 긴 회의도 처리된다
사용자로서, 2시간 회의도 요약되기를 바란다.
**인수 조건**: 입력 상한 초과 시 구간 분할 요약으로 자동 전환되고 화면에 그 사실이 표시된다.

### NS-011. 북마크로 중요한 대목을 표시한다
사용자로서, 듣다가 중요한 지점에 표시를 남기고 싶다.
**인수 조건**: 재생 중 북마크를 추가하면 시각과 메모가 저장되고, 노트 상단 목록에서 눌러 그 지점으로 이동한다.
