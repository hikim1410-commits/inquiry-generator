# 영수증 처리(OCR) 기능 PRD

문서 성격: 내비온 견적서 생성기의 3번째 문서 유형 추가를 위한 제품 요구사항 정의서(내부용).
작성 근거: `docs/research_영수증OCR_20260722/`의 `report.md`(조사 요약)·`facts.jsonl`(사실대장 F001~F015)·`verification-log.md`(팀리드 재검증 이력). 수치는 사실대장에 `confirmed`로 등재된 값만 (F00x) 근거를 붙여 인용하며, 미확정 항목은 [확인 필요]로 표기.

## 1. 개요

### 1.1 문서 정보

| 항목 | 내용 |
|---|---|
| 문서명 | 영수증 처리(OCR) 기능 PRD |
| 버전 | 0.1 (초안) |
| 작성일 | 2026-07-22 |
| 대상 제품 | 내비온 견적서 생성기 (Windows 데스크톱 앱) |
| 기능 위치 | 견적서 · 회의록에 이은 3번째 문서 유형 |

### 1.2 제품 요약

기존 견적서 생성기에 영수증·카드매출전표 이미지(사진/스캔) 또는 PDF를 드롭하면, LLM 비전이 상호·사업자번호·거래일시·금액 등 정산 필드를 구조화 JSON으로 추출하고, 도메인 규칙(항목합=총액, 공급가액+부가세=합계)으로 재검증한 뒤, 사용자가 원본 이미지와 나란히 확인·수정하고 확정하면 Excel 정산 세부내역으로 내보내는 기능. 회의록에서 확립한 "AI 초안 → 검토·수정 위저드 → 확정 산출물" 2단계 패턴을 영수증에 그대로 적용한다.

### 1.3 배경 — 왜 3번째 기능이 영수증인가

내비온 실무자는 정부지원사업 사업비 정산 시 다량의 영수증·카드전표를 손으로 옮겨 적어 Excel 세부내역과 전문가활용비 정산서를 작성한다. 이 옮겨 적기는 (1) 반복적이고 시간이 많이 들며, (2) 금액 오기입이 곧바로 정산 사고로 이어지는 고위험 작업이다. 회사 운영 원칙이 "정확성 우선 — 확인 불가 데이터는 [확인 필요] 표기, 추측 금지"인 만큼, 이 기능의 가치는 "완전 자동 입력"이 아니라 "사람이 검증하기 쉬운 초안을 빠르게 제공"하는 데 있다.

기술적으로도 착수 비용이 낮다. 앱은 이미 멀티프로바이더 LLM JSON 모듈(`src/ai/llm.py`), API 키 DPAPI 암호화 저장, 파일 드롭존, 2단계 위저드 UX, 회의록이라는 "문서 유형 추가" 선례를 보유한다. 실서비스 자가호스팅 경비앱 3곳(Receipt Wrangler·TaxHacker·firefly-receipt-scanner)이 모두 "멀티프로바이더 LLM + 구조화 출력 + 사용자 검토" 구조를 프로덕션에서 쓰고 있어(F005, F006), 앱이 이미 가진 자산과 동형이다.

## 2. 목표와 비목표

### 2.1 사업 목표

- 정산 증빙 영수증의 수작업 입력을 초안 자동화로 대체해 건당 처리 시간과 오기입을 줄인다.
- 기존 앱 아키텍처(멀티프로바이더 LLM·드롭존·위저드) 재사용으로 신규 의존성·배포 부피 증가를 최소화한다.
- 정확성 우선 원칙을 UI로 강제한다 — 검증 실패·저신뢰 필드는 사용자 확인 없이 산출물에 반영되지 않는다.

### 2.2 사용자 목표

- 영수증 여러 장을 한 번에 올려 상호·일시·금액을 자동으로 뽑아내고, 잘못된 값만 빠르게 고쳐 정산 세부내역을 완성한다.
- 원본 이미지와 추출값을 나란히 보며 금액이 맞는지 눈으로 대조한다.
- 카드번호 등 개인정보가 마스킹된 상태로만 저장·표기되도록 보장받는다.

### 2.3 비목표 (Non-goals)

조사에서 명시적으로 배제 결정된 항목. MVP는 물론 로드맵에서도 당분간 만들지 않는다.

- **자체 딥러닝 모델 학습**: Donut 영수증 예제의 기반 데이터셋 CORD는 인도네시아어(11,000+장)라 한국어에 못 쓴다(F002). Donut 자체도 2024-07 이후 정체(F011)이고, 한국어 영수증용 공개 가중치는 사실상 부재. 자체 학습 경로는 채택하지 않는다.
- **로컬 OCR 엔진 동봉(Tesseract·EasyOCR·PaddleOCR 등)**: PyInstaller onedir 배포(~16MB) 부피와 복잡도를 크게 키우는 반면, 한국어 영수증 특화 가중치가 없다. LLM 비전은 API 키만으로 동작한다(F007). 동봉하지 않는다.
- **오프라인 모드**: LLM 비전 방식의 구조적 한계로 오프라인 동작 불가(F007 비교표에 "Offline functionality: Not available" 명시). 오프라인 지원은 본 기능 범위에서 명시적으로 제외한다.
- **완전 무인 자동 반영**: 검토·수정 없이 추출값을 산출물에 자동 기입하는 흐름은 만들지 않는다. 사용자 확정이 항상 선행한다.

## 3. 사용자 페르소나

### 3.1 핵심 사용자

내비온(기술사업화 기관) 소속 정부지원사업 관리 실무자. 단일 페르소나로 설계한다(앱은 개인 데스크톱 단독 실행, 다중 사용자·역할 분리 없음).

| 항목 | 내용 |
|---|---|
| 이름(가칭) | 정산 담당 실무자 |
| 역할 | 사업비 경비 증빙 정리, 전문가활용비 정산서 ↔ Excel 세부내역 대조, 정산 서류 작성 |
| 기술 수준 | 일반 사무 사용자. 엑셀·한글 능숙, 코드/CLI 비사용 |
| 주 사용 맥락 | 정산 마감 시기에 영수증 수십~수백 장을 몰아서 처리 |
| 핵심 불편 | 영수증 금액·일시·상호를 손으로 옮겨 적는 반복 작업, 오기입 시 정산 반려 위험 |
| 성공 기준 | "옮겨 적기"가 "훑어보고 고치기"로 바뀌는 것. 틀린 값을 놓치지 않는 것 |

### 3.2 접근·권한 모델

앱은 로그인·서버·계정 개념이 없는 단일 사용자 데스크톱 앱이다. 따라서 전통적 인증/인가 대신 다음 세 가지가 "보안 접근" 요구사항을 대신한다. 관련 사용자 스토리는 US-013~US-015에 정의한다.

- API 키는 DPAPI로 암호화 저장(기존 자산 재사용). 평문 노출 금지.
- 영수증 이미지가 외부 LLM API로 전송된다는 사실을 최초 사용 시·설정 화면에서 고지.
- 카드번호는 마스킹된 형태로만 화면 표기·저장. 원본 전체 번호를 산출물·사이드카에 남기지 않는다.

## 5. 사용자 경험(UX) 흐름

### 5.1 진입점

- 사이드바 "영수증" 항목 클릭 → 영수증 뷰 전환(기존 뷰 전환 방식과 동일, JS `call('메서드')` → Python `Api`).
- 견적서·회의록과 달리 시작점은 "메모 입력"이 아니라 "파일 드롭"이다.

### 5.2 핵심 경험 (화면 단위)

```
[1] 영수증 뷰 진입
      │  (최초 1회) "이미지가 외부 AI API로 전송됩니다" 고지 배너
      ▼
[2] 드롭존 — 영수증 사진/스캔(jpg,png) · PDF 여러 개 드롭 또는 파일선택
      │  PDF는 페이지별 이미지로 렌더(pypdfium2)
      ▼
[3] 자동 추출 (진행 표시: i/total, 파일명)
      │  각 건: 이미지 base64 → LLM 비전 → 스키마 JSON → 도메인 검증
      ▼
[4] 검토·수정 위저드  ┌─────────────┬─────────────────────────┐
      │               │  원본 이미지 │  추출 필드(수정 가능)     │
      │               │  (확대 가능) │  상호 [ㅇㅇ상사]          │
      │               │              │  거래일시 [2026-06-11]     │
      │               │              │  합계 [55,000] ⚠불일치     │
      │               │              │  카드번호 [1234-****-**78] │
      │               └─────────────┴─────────────────────────┘
      │   ⚠ = 항목합≠총액 / 저신뢰 필드 강조. [확인 필요] 배지.
      ▼
[5] 건별 확정 → 전체 확정
      ▼
[6] Excel 정산 세부내역 내보내기 (행 누적 + 합계 검증 컬럼)
```

### 5.3 상태·예외 경험

- 파싱 실패 건: 목록에서 빨간 배지, "이 건만 다시 시도" 버튼. 나머지 건 진행은 막지 않는다.
- 스캔 품질 불량·비영수증 이미지: 필드 대량 누락 시 "인식 실패 가능 — 원본 확인" 안내.
- 합계 불일치: 값을 자동 보정하지 않고 경고만 — 정확성 우선 원칙(사람이 원본 보고 판단).
- API 키 미설정: 설정 화면 유도(회의록·견적서와 동일 흐름).

### 5.4 UI/UX 하이라이트

- 원본-추출값 좌우 병치는 조사에서 확인된 전 사례 공통 패턴(firefly-receipt-scanner "Review and edit extracted data before creating transactions", TaxHacker 동일). 눈 대조가 곧 검증이다.
- 저신뢰/불일치 필드의 시각 강조로 사용자가 어디를 봐야 하는지 즉시 파악.
- 회의록 검토 팝업과 상호작용 언어를 통일해 학습 비용 최소화.

## 6. 추출 필드 정의

MVP 추출 스키마의 기본 필드. 내비온 정산 양식과의 최종 대조·확정은 [확인 필요](10절 미해결 질문 Q3).

| 필드 | 키(가안) | 타입 | 설명 · 규칙 |
|---|---|---|---|
| 상호 | `store_name` | STRING | 가맹점/상호명. 불명확 시 빈값 + `[확인 필요]` |
| 사업자등록번호 | `biz_no` | STRING | `000-00-00000` 형식. 없으면 빈값 |
| 거래일시 | `tx_datetime` | STRING | `YYYY-MM-DD HH:MM`. 날짜만 있으면 시간 생략 |
| 공급가액 | `supply_amount` | INTEGER | 원 단위 정수. 없으면 0 |
| 부가세 | `vat` | INTEGER | 원 단위 정수. 없으면 0 |
| 합계 | `total_amount` | INTEGER | 원 단위 정수. 결제 총액 |
| 승인번호 | `approval_no` | STRING | 카드 승인번호. 없으면 빈값 |
| 카드번호(마스킹) | `card_no_masked` | STRING | **마스킹 상태로만** 저장. 원본 전체번호 금지 |
| 품목 리스트 | `items` | ARRAY | `[{name, qty, price}]`. 항목합=총액 검증용 |
| 검증·신뢰 메타 | `_flags` | ARRAY | `sum_mismatch`, `low_confidence:<field>`, `needs_review:<field>` 등 |

검증 규칙(FR-05):
- `sum(items[].price*qty)` 와 `total_amount` 불일치 → `sum_mismatch` 플래그.
- `supply_amount + vat` 와 `total_amount` 불일치 → `vat_mismatch` 플래그.
- 플래그가 있어도 값은 자동 수정하지 않고 사용자 검토로 넘긴다(F008 instructor 예제의 model_validator 방식 참고 — 검증은 하되 환각 자동정정은 하지 않음).

## 7. 기술 설계 개요

### 7.1 모듈 골격 (회의록 선례 동형)

회의록이 `src/minutes/`(빌더) + `src/ai/minutes.py`(AI) + `src/api/minutes.py`(엔드포인트) + 믹스인 조립으로 구성된 것과 동일하게 배치.

```
src/receipt/            # 영수증 도메인 (Excel 빌더, PDF→이미지 렌더, 검증 규칙)
    __init__.py
    xlsx_receipt.py     # openpyxl 정산 세부내역 생성 (FR-08)
    pdf_render.py       # PDF → 페이지 이미지 (pypdfium2, FR-02)
    verify.py           # 항목합=총액 / 공급가+부가세=합계 (FR-05)
src/ai/receipt.py       # RECEIPT_SCHEMA + 프롬프트 + 정규화 + extract_receipt()
                        #   (minutes.py 동형: build_*_prompt / _normalize_* / 공개함수)
src/api/receipt.py      # ReceiptApi 믹스인 — 드롭·추출·검토·내보내기 엔드포인트
```

조립 지점(기존 파일 최소 수정):
- `src/api/__init__.py`: `class Api(SettingsApi, QuoteApi, MinutesApi, ReceiptApi, SystemApi, ApiCore)` 에 `ReceiptApi` 추가.
- `src/api/core.py`: `_DROPZONES` 튜플에 `("#receipt-dropzone", "receipt")` 한 줄 추가 — 네이티브 DnD 경로 획득이 그대로 붙는다.

### 7.2 llm.py 이미지 확장 (핵심 변경)

`complete_json(...)`는 현재 텍스트 전용이다(프롬프트 문자열만). 이미지 입력을 위해 선택 파라미터(예: `images: list[base64]`)를 추가하고, 프로바이더별 payload 구성부에서 이미지 파트를 삽입한다. 스키마 강제·재시도·오류 매핑 로직은 그대로 재사용한다.

- Gemini: `contents[].parts[]`에 `{"inline_data": {"mime_type": "image/png", "data": <base64>}}` 파트 추가.
- OpenAI: `messages[].content`를 배열로 바꿔 `{"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}}` 포함.
- Anthropic: `messages[].content`를 배열로 바꿔 `{"type": "image", "source": {"type": "base64", ...}}` 포함.

세 프로바이더 모두 base64 이미지 입력을 지원한다(조사 확인). 기존 텍스트 호출은 `images` 미지정 시 완전히 동일하게 동작(하위호환).

### 7.3 파이프라인

```
드롭(이미지/PDF) → [PDF면 pdf_render로 이미지화] → base64 인코딩
   → ai/receipt.extract_receipt(provider, images, schema=RECEIPT_SCHEMA)
   → llm.complete_json(..., images=...)  (스키마 강제 JSON)
   → _normalize_receipt (누락·마스킹·플래그)
   → receipt/verify (합계 검증 → 플래그 부착)
   → 검토·수정 위저드 (사용자 확정)
   → receipt/xlsx_receipt (Excel 행 누적)
```

### 7.4 재사용 자산 (신규 의존성 최소화)

| 자산 | 재사용 방식 |
|---|---|
| `src/ai/llm.py` | 이미지 파라미터만 확장, 나머지 그대로 |
| 스키마 강제(`gemini_to_jsonschema`) | RECEIPT_SCHEMA에 그대로 적용 |
| 드롭존(`ApiCore._DROPZONES`) | 셀렉터 1개 추가 |
| API 키 DPAPI 저장 | 그대로 |
| openpyxl | Excel 산출물(FR-08) |
| 위저드 UX(회의록) | 검토·수정 팝업 패턴 이식 |

신규 의존성 후보는 **PDF→이미지 렌더러 1종뿐**(pypdfium2 — 조사에서 이미 검증 도구로 사용된 바 있음). 기존 kordoc은 PDF를 텍스트(마크다운)로 뽑는 경로라 비전 입력에는 부적합 → 이미지 렌더는 별도 필요.

## 8. 성공 지표

### 8.1 사용자 중심

- **필드 정확도(파일럿 게이트)**: 내비온 실영수증 N장(권장 N=30~50, 최종 N은 [확인 필요])에 대해 핵심 4필드(상호·거래일시·합계·사업자번호)의 필드 단위 정확도가 사전 합의 임계치 이상. 임계치 미달 시 MVP 착수 보류 또는 폴백 프로바이더(FR-22) 검토. (공개 벤치마크 부재 — 자체 파일럿으로만 판정. F015 등 미검증 정확도 수치는 게이트 기준으로 쓰지 않는다.)

- 정산 준비 소요 시간 감소(정성 인터뷰 + 처리 건수 로그).
- 오기입으로 인한 정산 반려/재작업 건수 감소.

### 8.3 기술

- 건당 처리 시간(추출 API 왕복 포함) 목표치 내.
- 파싱 실패율(재시도 후에도 실패) 상한 관리.
- 합계 검증 플래그가 실제 오추출을 잡아내는 비율(검증 유효성).

## 12. 사용자 스토리

모든 스토리는 테스트 가능하도록 수용 기준을 구체화한다. 이 앱은 로그인이 없는 단일 사용자 데스크톱 앱이므로, 인증/인가 대신 "보안 접근"에 해당하는 API 키 보호·외부 전송 고지·개인정보 마스킹을 US-013~US-015로 포함한다.

### US-001. 영수증 뷰 진입
- 설명: 사용자로서, 사이드바에서 "영수증"을 선택해 영수증 처리 화면으로 전환하고 싶다.
- 수용 기준:
  - 사이드바에 "영수증" 항목이 표시된다.
  - 클릭 시 영수증 뷰로 전환되고 드롭존이 보인다.
  - 견적서·회의록 뷰와 상호 전환이 정상 동작한다.

### US-002. 다건 이미지 업로드
- 설명: 사용자로서, 영수증 사진(jpg/png) 여러 장을 한 번에 드롭하거나 파일선택으로 올리고 싶다.
- 수용 기준:
  - 드롭존에 여러 이미지 파일을 드롭하면 전체 경로가 접수된다.
  - 파일선택 버튼으로도 다중 선택이 가능하다.
  - 지원하지 않는 형식은 접수 목록에서 사유와 함께 제외 표시된다.

### US-003. PDF 업로드와 이미지 변환
- 설명: 사용자로서, PDF 영수증을 올리면 자동으로 이미지로 변환되어 사진과 동일하게 처리되길 원한다.
- 수용 기준:
  - PDF 접수 시 페이지별 이미지로 렌더된다.
  - 다중 페이지 PDF의 각 페이지가 개별 처리 대상이 된다.
  - 렌더 실패 시 해당 파일만 오류로 표시되고 나머지 처리는 계속된다.

### US-004. LLM 비전 자동 추출
- 설명: 사용자로서, 올린 영수증에서 상호·일시·금액 등 필드가 자동으로 추출되길 원한다.
- 수용 기준:
  - 각 건이 LLM 비전으로 전송되어 6절 스키마의 필드가 채워진다.
  - 진행 상황이 i/total·파일명으로 표시된다.
  - 응답은 스키마 강제 JSON으로 파싱되며, 비정형 응답은 재시도 후 실패 처리된다.

### US-005. 누락 필드 플래그
- 설명: 사용자로서, 인식하지 못한 필드가 임의 값으로 채워지지 않고 [확인 필요]로 표시되길 원한다.
- 수용 기준:
  - 인식 실패 필드는 빈값 + `[확인 필요]` 배지로 표시된다.
  - 저신뢰 필드는 `low_confidence`/`needs_review` 플래그로 강조된다.
  - 어떤 필드도 추측 값으로 자동 채워지지 않는다.

### US-006. 합계 검증
- 설명: 사용자로서, 항목 합계와 총액이 맞지 않으면 경고를 받고 싶다.
- 수용 기준:
  - `sum(items)` ≠ `total_amount`이면 `sum_mismatch` 경고가 표시된다.
  - `supply_amount + vat` ≠ `total_amount`이면 `vat_mismatch` 경고가 표시된다.
  - 검증 실패 시 값이 자동 보정되지 않고 사용자 검토로 넘어간다.

### US-007. 원본-추출값 병치 검토
- 설명: 사용자로서, 원본 이미지와 추출된 값을 나란히 보며 대조하고 싶다.
- 수용 기준:
  - 좌측 원본 이미지(확대 가능)와 우측 추출 필드가 함께 표시된다.
  - 불일치·저신뢰 필드가 시각적으로 강조된다.
  - 여러 건을 순차적으로 검토할 수 있다.

### US-008. 필드 인라인 수정
- 설명: 사용자로서, 추출값이 틀렸을 때 그 자리에서 고치고 싶다.
- 수용 기준:
  - 각 필드를 인라인으로 편집할 수 있다.
  - 금액 필드 수정 시 합계 검증이 재계산되어 경고가 갱신된다.
  - 수정 내용이 확정 전까지 유지된다.

### US-009. 확정 게이트
- 설명: 사용자로서, 내가 확정하기 전에는 어떤 값도 산출물에 반영되지 않길 원한다.
- 수용 기준:
  - "확정" 동작 전에는 Excel 내보내기가 해당 건을 포함하지 않는다.
  - 건별 확정과 전체 확정이 구분된다.
  - 미확정·검증 실패 건은 확정 시 경고로 안내된다.

### US-010. Excel 정산 세부내역 내보내기
- 설명: 사용자로서, 확정한 영수증들을 Excel 정산 세부내역으로 한 번에 내보내고 싶다.
- 수용 기준:
  - 확정된 다건이 한 시트에 행으로 누적된다.
  - 상호·일시·공급가액·부가세·합계·승인번호·마스킹 카드번호 컬럼이 포함된다.
  - 합계 검증 결과 컬럼이 포함되고, 금액 합계가 정확히 계산된다.
  - 한글·특수문자가 깨지지 않고 파일이 정상적으로 열린다.

### US-011. 건별 오류 처리와 재시도
- 설명: 사용자로서, 일부 영수증 인식이 실패해도 나머지는 진행되고 실패 건만 다시 시도하고 싶다.
- 수용 기준:
  - 파싱 실패 건이 목록에서 구분 표시된다.
  - "이 건만 다시 시도"로 개별 재처리가 가능하다.
  - 한 건의 실패가 전체 배치를 중단시키지 않는다.

### US-012. 비영수증·저품질 이미지 안내
- 설명: 사용자로서, 영수증이 아닌 이미지나 흐린 스캔을 올렸을 때 인식 실패 가능성을 안내받고 싶다.
- 수용 기준:
  - 필드가 대량 누락되면 "인식 실패 가능 — 원본 확인" 안내가 표시된다.
  - 해당 건은 확정 전 검토 필수로 표시된다.

### US-013. API 키 보안 저장 (보안 접근)
- 설명: 사용자로서, 입력한 LLM API 키가 평문으로 노출되지 않고 안전하게 저장되길 원한다.
- 수용 기준:
  - API 키는 DPAPI로 암호화 저장된다(기존 자산 재사용).
  - 설정 화면·로그·산출물 어디에도 평문 키가 남지 않는다.
  - 키 미설정 시 추출 시도는 설정 화면으로 유도된다.

### US-014. 외부 전송 고지 (보안 접근)
- 설명: 사용자로서, 영수증 이미지가 외부 AI API로 전송된다는 사실을 사전에 고지받고 싶다.
- 수용 기준:
  - 영수증 뷰 최초 진입 시 외부 전송 고지가 1회 표시된다.
  - 설정 화면에서도 해당 고지를 다시 확인할 수 있다.
  - 고지는 오프라인 미지원 사실을 포함한다.

### US-015. 카드번호 마스킹 (보안 접근)
- 설명: 사용자로서, 카드번호가 마스킹된 형태로만 저장·표기되어 개인정보가 보호되길 원한다.
- 수용 기준:
  - 추출 단계에서 카드번호 중간 자리가 마스킹된다(예: `1234-****-****-5678`).
  - 화면·Excel·사이드카 어디에도 전체 카드번호가 저장되지 않는다.
  - 마스킹 처리는 사용자 수정으로 해제되지 않는다.

### US-016. 처리 건수·사용량 가시화
- 설명: 사용자로서, 이번 세션에 처리한 영수증 건수를 확인하고 싶다.
- 수용 기준:
  - 처리 건수가 화면에 표시된다.
  - (향후) 건당 비용 추정과 연결될 수 있는 형태로 집계된다.
