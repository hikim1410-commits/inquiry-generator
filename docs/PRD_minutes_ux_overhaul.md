# 회의록 작성·매핑 편집기 UX 개선 PRD

## 1. 개요 및 배경

### 문서 정보
- 문서명: 회의록 작성 화면·HWPX 매핑 편집기 UX 개선 제품 요구사항 정의서(PRD)
- 버전: v1.0 (UX 개선 후속 — `docs/PRD_minutes_hwpx_enhancement.md` v1.2의 후속 문서)
- 대상 제품: 내비온 견적서·회의록 생성기 (Python + pywebview 데스크톱 앱)
- 범위 구분: **신규 프로젝트가 아니라, 이미 동작하는 회의록 기능 위에 얹는 UX 개선 작업**

### 한 줄 요약
이 문서는 "회의록을 만드는 사람"이 매일 마주하는 세 화면(① 매핑 편집기의 항목 패널, ② 회의 내용 입력칸, ③ 회의 메모 카드)을 더 쉽고 자연스럽게 바꾸기 위한 요구사항을 정의한다. 엔진(HWPX 셀 쓰기)·저장 포맷·생성 흐름은 그대로 두고, **사람이 보고 만지는 표면(UI)만** 바꾸는 것이 핵심이다.

### 배경
선행 PRD(v1.2)에서 정의·구현된 결과로 현재 앱은 다음을 갖추고 있다(실제 코드 확인).
- 회의록 매핑 편집기는 더 이상 "읽기 전용 표"가 아니라, 양식 그림 위를 클릭해 핀을 찍는 **이미지-핀 편집기**다(`ui/app.js` `openMinutesMapEditor` 2093행~, `renderMapCanvas` 2171행~, 모달 마크업 `ui/index.html` 700~734행).
- 우측 패널 "표준 항목 매핑"(`ui/index.html` 722행 `<h4>표준 항목 매핑</h4>`, `#mn-map-status`)은 **고정된 표준 7항목**(`MN_SLOT_ORDER`, `ui/app.js` 1907행)의 매핑 현황을 보여준다.
- 회의 내용 입력은 행마다 드롭다운(■제목/•항목/└하위/빈줄) + 입력칸 + 삭제버튼이 쌓이는 **블록형 에디터**다(`addSectionRow` `ui/app.js` 1818행, `SECTION_TYPE_LABELS` 1817행, 마크업 `ui/index.html` 311~316행).
- 회의 메모는 `#mn-memo` textarea(`rows="10"`, `ui/index.html` 268행)다.
- 저장 포맷은 `.minutes.fieldmap.json` version 2로, `cell_map` + `custom_slots` + `annotations`를 담는다(`src/ai/minutes_template_mapper.py` `save_minutes_cellmap` 302행~).

이 문서가 다루는 세 가지 불편은 다음과 같다.
1. 우측 "표준 항목 매핑" 패널이 **고정 7항목**이라, 사용자 양식에 맞는 임의 라벨의 상단 항목 세트를 직접 정의할 수 없다.
2. 회의 내용 블록 에디터가 행마다 드롭다운·버튼이 쌓여 **글 쓰듯 입력하기 불편**하다.
3. 회의 메모 카드가 textarea 아래로 **불필요한 빈 여백**을 크게 남긴다.

### 설계 철학 (반드시 준수)
- 최소 변경·과설계 금지. 가장 단순하게 동작하는 안을 먼저 제시하고, 더 무거운 대안은 "필요 시"로 분리한다.
- 외부 의존성 추가 금지. 바닐라 JS·오프라인·한글(COM) 미설치 환경 동작 보장을 유지한다.
- HWPX 셀 쓰기 엔진(`build_minutes`)·생성 흐름(`generate_minutes`)은 **변경하지 않는다**. UI 레이어에서 기존 데이터 모델(`cell_map`/`custom_slots`/`sections`)로 환원해 엔진을 그대로 먹인다.
- 후방호환 100%. 기존 `config.json`·`.minutes.fieldmap.json`·`minutes.json`을 가진 사용자가 재설정 없이 그대로 동작해야 한다.

## 2. 목표 및 비목표

### 비즈니스 목표 (Business Goals)
- B1. 비개발 작성자가 자기 양식에 맞는 **상단 고정 항목 세트를 직접 정의**(추가·이름변경·삭제·순서변경)해, 발주처·부서별 임의 양식에서도 매핑을 직관적으로 완성하게 한다.
- B2. 회의 내용을 **글 쓰듯 자유롭게 작성**하게 해, 블록 에디터의 클릭 피로를 없애고 작성 시간을 단축한다.
- B3. 회의 메모 입력 영역의 시각적 군더더기를 제거해, 한 화면에 더 많은 정보가 들어오게 한다.
- B4. 위 모든 개선이 **기존 회의록 생성·재편집 결과를 1bit도 바꾸지 않도록** 후방호환을 유지한다.

### 사용자 목표 (User Goals)
- U1. "내 양식에는 '과제명·작성자·배석자'가 있는데, 앱이 강요하는 '사업명·총인원' 라벨 대신 내 라벨로 항목을 만들고 순서도 내 양식대로 두고 싶다."
- U2. "회의 내용은 메모장에 쓰듯 줄 단위로 빠르게 쓰고, 제목/불릿/하위는 자연스러운 기호로 표현하고 싶다."
- U3. "회의 메모칸이 텅 빈 채로 화면을 잡아먹지 않았으면 좋겠다."

### 비목표 (Non-Goals)
- N1. HWPX 셀 쓰기 엔진(`build_minutes`)·생성 API(`generate_minutes`)·`scan_hwpx_grid` 좌표 계약 변경은 하지 않는다(선행 PRD v1.2 A-6 범위로 이미 견고화됨, 본 문서는 그 위에 UI만 얹음).
- N2. 회의 내용에 대한 리치 텍스트(굵게·색·표·이미지) 편집은 하지 않는다. 경량 서식(제목/불릿/하위/빈줄)만 다룬다.
- N3. 매핑 편집기의 이미지-핀 클릭 메커니즘(핀 찍기·셀 역추적) 자체는 바꾸지 않는다. 요구사항 1은 **우측 항목 패널의 데이터 모델·표시**만 바꾼다.
- N4. 견적서(.hwp, COM 경로)에는 적용하지 않는다(회의록 HWPX 한정).
- N5. 마크다운 전체 문법(링크·코드블록·표 등) 지원은 하지 않는다. 회의록 4서식에 1:1 대응하는 최소 마크업만 쓴다.
- N6. 클라우드 동기화·다중 사용자·협업은 범위 밖이다(로컬 단일 사용자 데스크톱 앱 전제 유지).

## 3. 사용자 페르소나

### 핵심 사용자 유형
- **작성자(내부 직원)**: 비개발자. 한글·엑셀에는 익숙하나 좌표·JSON·"슬롯" 개념은 낯설다. 회의가 끝나면 메모/녹취로 회의록 HWPX를 만든다.
- **운영자(검수·관리자)**: 팀 표준 양식을 배포·관리한다. 양식별 항목 세트를 한 번 세팅해 팀이 같은 걸 쓰길 원한다.

### 페르소나 상세
- **김주임 (작성자)**: 발주처 양식에는 "과제명·작성자·배석자" 같은 칸이 있는데, 앱은 "사업명·총인원"만 보여줘 매번 머릿속으로 번역한다. "내 양식 그대로 항목 이름을 바꾸고 순서도 맞추고 싶다." 회의 내용도 드롭다운을 매번 고르는 게 번거로워, "그냥 메모장처럼 쓰고 싶다."
- **이과장 (운영자)**: 양식을 한 번 등록·매핑해두면 팀원이 같은 항목 세트를 쓰길 원한다. 항목 라벨이 양식과 일치해야 팀원이 헷갈리지 않는다.

### 역할 기반 접근(RBAC) 관점
- 로컬 단일 사용자 데스크톱 앱으로 로그인·다중 역할 권한 체계가 없다. 전통적 인증/인가는 적용되지 않는다.
- 보안 경계는 존재한다: AI API 키는 `config_store.encrypt_secret`(Windows DPAPI, 현재 사용자 계정 바인딩)로 암호화 저장된다. 본 문서의 세 개선은 **AI 키 유무와 무관하게 동작**해야 한다(항목 편집·텍스트 작성·메모 입력은 전부 오프라인·로컬 연산). 관련 보안 스토리는 US-013 참조.

## 4. 기능 요구사항

각 요구사항에 `[재사용]`(기존 코드/모델 그대로 활용) 또는 `[신규]`(새 구현)와 근거 파일·함수를 명시한다. 우선순위는 P0(필수)·P1(중요)·P2(여유).

### 요구사항 1 — "표준 항목 매핑"을 자유 설정형 "상단 고정 항목"으로 전환

현재 우측 패널(`renderSlotStatus`, `ui/app.js` 2317~2335행)은 고정 `MN_SLOT_ORDER` 7항목만 행으로 나열한다. 이를 사용자가 자유롭게 다루는 **항목 리스트**로 바꾼다.

- **1-A. 상단 고정 항목 리스트 UI [신규] · P0**
  - 우측 패널을 "표준 7항목 현황"에서 **편집 가능한 항목 리스트**로 교체한다. 각 항목 행에 라벨, 매핑된 셀 좌표(또는 "미지정"), 그리고 액션(이름변경·삭제·위/아래 이동)을 둔다.
  - 하단에 "＋ 항목 추가" 버튼을 둔다. 추가하면 라벨을 입력받고, 사용자가 캔버스에서 셀을 클릭(기존 핀 메커니즘)해 해당 항목에 셀을 연결한다.
  - 표준 7항목은 **삭제된 상태가 아니라 "기본 제공 프리셋"으로 초기 채움**된다. 사용자는 그중 불필요한 것을 삭제하거나 라벨을 바꿀 수 있다.
- **1-B. 표준/커스텀 항목의 의미 보존 [신규·핵심] · P0**
  - 핵심 제약: 표준 7항목은 단순 라벨이 아니라 **AI 초안·2단계 폼과 연결된 의미 슬롯**이다(`business_name`은 사업명 입력값, `content`는 섹션 렌더링, `participants`는 다중 줄). 따라서 항목을 "완전 평면화"하면 값 공급원이 끊긴다.
  - 해결: 각 항목은 내부적으로 **두 종류** 중 하나로 구분한다.
    - **표준 연결 항목** (`slot` 보유): 라벨은 사용자가 자유 변경하되, 값은 기존 의미 파이프라인(`slot` → `cell_map`)에서 공급된다. 라벨 변경은 **편집기 표시·식별용**일 뿐 생성 결과를 바꾸지 않는다(양식의 인쇄된 라벨은 HWPX 템플릿 셀에 이미 있고, 우리는 값 셀만 채운다).
    - **커스텀 항목** (`slot` 없음): 사용자가 직접 입력하는 정적 텍스트. 기존 `custom_slots`/`data.custom_fields` 경로로 셀에 기록된다(`hwpx_minutes.py` 259~268행 이미 구현).
  - "회의 내용"(`content`)은 본문 블록이므로 상단 항목 리스트의 순서변경 대상에서 분리해 별도 고정으로 둔다(요구사항 2와 연결).
- **1-C. 순서변경·이름변경·삭제·추가 [신규] · P0**
  - 순서: 항목 리스트의 배열 순서로 표현한다(위/아래 버튼. 드래그는 P2 "필요 시").
  - 이름변경: 라벨 인라인 편집. 표준 연결 항목도 라벨 변경 허용(의미 슬롯은 유지).
  - 삭제: 항목 제거. 표준 항목 삭제 = 해당 슬롯을 매핑·표시에서 제외(생성 시 빈 칸, 기존 미매핑 정책과 동일).
  - 추가: 새 커스텀 항목(라벨 + 클릭으로 셀 연결).
- **1-D. 데이터 모델 통합·마이그레이션 [신규] · P0** — 8장 "데이터 모델 변경" 참조.

### 요구사항 2 — "회의 내용" 블록 에디터를 텍스트 편집기 방식으로 전환

현재(`ui/index.html` 311~316행, `addSectionRow` `ui/app.js` 1818행)는 행마다 select+input+삭제버튼이 쌓인다. 이를 **단일 텍스트 입력 + 경량 마크업 파서**로 바꾼다.

- **2-A. 텍스트 편집기 입력 [신규] · P0**
  - `#mn-r-sections`(블록 컨테이너)와 "＋ 항목 추가" 버튼(`#mn-r-add-section`)을 **단일 `<textarea>`**(예: `#mn-r-content-text`)로 교체한다.
  - 사용자는 줄 단위로 자유롭게 타이핑한다. 경량 마크업으로 4서식을 표현한다(아래 2-B).
- **2-B. 마크업 ↔ 섹션 매핑 규칙 [신규] · P0**
  - 기존 섹션 타입(`header`/`bullet`/`sub`/`empty`)과 1:1 대응하는 최소 규칙:
    | 입력 줄 | 섹션 타입 | 비고 |
    |---|---|---|
    | `# 안건 검토` (앞에 `# `) | `header` (■ 제목) | |
    | `- 일정 확정` (앞에 `- `) | `bullet` (• 항목) | |
    | `  - 세부 담당자` (들여쓰기 2칸+ 후 `- `) | `sub` (└ 하위) | 탭 또는 공백 2칸 |
    | (빈 줄) | `empty` (빈 줄) | |
    | 마커 없는 일반 줄 | `bullet` | 정규화 시 `- ` 부여 |
  - `parseSectionsText(text) → [{type, text}]` 와 `sectionsToText(sections) → text` 두 순수 함수로 구현. **왕복(round-trip) 안정성** 보장: 한 번 정규화된 텍스트는 파싱→직렬화 시 동일하게 복원된다.
- **2-C. 기존 블록 데이터 호환 [신규] · P0**
  - 2단계 진입 시(`renderMinutesReview`, `ui/app.js` 1784행) AI 초안의 `draft.sections`를 `sectionsToText`로 직렬화해 textarea를 채운다.
  - 생성 시(`collectMinutesPayload`, `ui/app.js` 1836행) textarea 값을 `parseSectionsText`로 다시 `sections` 배열로 환원해 **기존 payload 형태(`sections:[{type,text}]`) 그대로** `generate_minutes`에 전달한다. 백엔드·엔진 무변경.
- **2-D. 권장 구현안: textarea + 라이트 파서 (contenteditable 아님) · P0**
  - 8장 "기술 트레이드오프"에서 비교. 결론: **단순 `<textarea>` + 정규식 라인 파서** 채택.

### 요구사항 3 — "회의 메모" 카드 여백/비율 조정

`#mn-memo`(`ui/index.html` 268행)의 과도한 높이·여백을 바로잡는다.

- **3-A. 근본 원인 제거 [신규·CSS] · P0**
  - 원인(코드 확인): ① `#mn-memo`는 `.minutes-form` 안에 있어 `app.css` 190~198행의 폼 textarea 스타일(`width:100%`·`box-sizing:border-box`·`min-height`) 적용 대상(`.editor-form`/`.settings-layout`/`.modal`)에서 **제외**된다 → 브라우저 기본 textarea 메트릭으로 렌더(폭 미충전·고정 높이). ② `rows="10"`이 내용과 무관하게 약 10줄 높이를 고정해, 짧은 메모일 때 카드 하단에 빈 공간이 크게 남는다.
  - 처방: `#mn-memo`에 `width:100%; box-sizing:border-box; resize:vertical`을 부여하고 기본 높이를 내용에 맞는 수준(약 5~6줄, `min-height` 또는 `rows` 축소)으로 낮춘다. 9장 "구체적 CSS 처방" 참조.

## 5. 사용자 경험 플로우

### 진입점 (Entry Points)
- 요구사항 1: 회의록 양식 갤러리 → 양식 카드의 "매핑 편집"(이미지-핀 모달, `#mn-map-modal`).
- 요구사항 2·3: 회의록 작성 위저드 → 1단계(메모/첨부, `#minutes-step1`) 및 2단계(검토·수정, `#minutes-step2`).

### 핵심 경험 — 작성자 시점 (요구사항 1)
```
[매핑 편집 모달]
 ┌─ 양식 그림(클릭해 핀 찍기) ─┐   ┌─ 상단 고정 항목 ───────────┐
 │  ▒ 사업명 ▒ [값칸]         │   │ ☰ 사업명      (1,1)  ✎ 🗑 ↑↓ │
 │  ▒ 일 시 ▒ [값칸]📌        │   │ ☰ 회의 일시    (2,1)  ✎ 🗑 ↑↓ │
 │  ▒ 장 소 ▒ [값칸]          │   │ ☰ 배석자(커스텀)(4,2) ✎ 🗑 ↑↓ │
 │  ...                       │   │ [＋ 항목 추가]               │
 └───────────────────────────┘   └────────────────────────────┘
```
1. 사용자가 양식의 매핑 편집을 연다. 우측에 표준 7항목이 **기본 프리셋**으로 채워져 있다.
2. 자기 양식에 맞게 "사업명"을 "과제명"으로 이름변경하고, 불필요한 "총 인원"을 삭제하고, 양식에 있는 "배석자"를 "＋ 항목 추가"로 새로 만든다.
3. "배석자"를 추가한 뒤 양식 그림에서 해당 값 셀을 클릭해 핀을 찍어 연결한다.
4. 순서를 양식 모양대로 위/아래로 정렬하고 저장한다. → `cell_map`(표준 항목)과 `custom_slots`(커스텀 항목)가 도출되어 `.minutes.fieldmap.json`에 저장된다. 엔진은 기존대로 이 둘을 먹는다.

### 핵심 경험 — 작성자 시점 (요구사항 2)
```
[2단계: 회의 내용]
 ┌─ 회의 내용 (글 쓰듯 입력) ──────────────┐
 │ # 안건 검토                              │
 │ - 일정 확정                              │
 │   - 7월 2주차 착수                       │
 │                                          │
 │ # 결정 사항                              │
 │ - 예산 재배정 승인                       │
 └──────────────────────────────────────────┘
```
1. 2단계에 들어가면 AI 초안 내용이 위 마크업 텍스트로 채워져 있다.
2. 사용자는 메모장처럼 줄을 추가·삭제·수정한다. 드롭다운을 누를 필요가 없다.
3. 생성 버튼을 누르면 텍스트가 `sections` 배열로 환원되어 기존과 동일한 HWPX가 만들어진다.

### 핵심 경험 — 작성자 시점 (요구사항 3)
- 1단계 회의 메모칸이 입력 폭을 꽉 채우고, 짧은 메모를 붙여도 카드가 내용에 맞는 높이로 보여 화면이 깔끔하다.

### UI/UX 하이라이트
- 좌표(row,col)는 사용자에게 숫자보다 **항목 행 + 클릭 핀**으로 인지된다.
- 항목 라벨은 사용자 양식의 실제 라벨과 일치시킬 수 있어 인지 부하가 준다.
- 회의 내용은 "양식 강요" 없이 글쓰기 흐름을 유지한다.
- 모든 안내·경고는 한국어. 기존 토스트(`toast`)·상태 텍스트 패턴 재사용.
- 비가역 동작(항목 삭제)은 즉시 반영하되, 저장 전까지 모달을 닫지 않으면 되돌릴 수 있게 한다(저장 시 확정).

## 6. 내러티브

김주임은 발주처 회의록 양식을 앱에 등록한다. 예전 같으면 앱이 보여주는 "사업명·총인원" 같은 고정 항목을 머릿속으로 자기 양식의 "과제명·배석자"로 번역하며 어느 칸이 어디인지 헷갈렸다. 이제는 우측 항목 리스트에서 "사업명"을 "과제명"으로 바꾸고, 쓰지 않는 "총 인원"을 지우고, 양식에 있는 "배석자"를 새 항목으로 추가한 뒤 양식 그림에서 그 칸을 클릭해 연결한다. 항목 순서까지 양식 그대로 맞췄다. 회의가 끝나자 그는 회의 내용을 메모장에 쓰듯 줄줄 적어 내려간다 — 제목은 `#`, 항목은 `-`, 하위는 들여쓰기. 드롭다운을 단 한 번도 누르지 않았다. 1단계 메모칸도 더 이상 화면을 텅 빈 채로 잡아먹지 않는다. 생성 버튼을 누르자, 바뀐 건 그의 작업 경험뿐 — HWPX 결과물은 예전과 똑같이 정확하게 칸에 들어간다.

### 데이터 모델 변경 (요구사항 1 — 통합 스키마·후방호환)

핵심 통찰: **"상단 고정 항목" = 표준 의미 슬롯 항목과 커스텀 정적 항목을 하나의 순서 있는 리스트로 보여주는 표시 레이어**다. 엔진이 먹는 것은 여전히 ① 표준 슬롯의 `cell_map`, ② 커스텀의 `custom_slots`/`custom_fields`다. 따라서 새 필드는 **편집기용 메타(라벨·순서·종류)** 만 추가하면 된다.

권장: `.minutes.fieldmap.json`을 **version 3**으로 확장하되, 새 키 `top_items`는 **선택적·파생 가능**하게 둔다.
```jsonc
{
  "version": 3,
  "template": "발주처_회의록.hwpx",
  "is_standard": false,
  "cell_map":   { "business_name": [1,1], "meeting_date": [2,1] },   // 기존 — 표준 슬롯
  "custom_slots":[{ "id": "attendees_ext", "label": "배석자", "cell": [4,2] }], // 기존
  "annotations":[ ... ],                                              // 기존(이미지-핀)
  "top_items": [                                                       // 신규(선택)
    { "id": "business_name", "label": "과제명",   "slot": "business_name", "order": 0 },
    { "id": "meeting_date",  "label": "회의 일시","slot": "meeting_date",  "order": 1 },
    { "id": "attendees_ext", "label": "배석자",   "order": 2 }          // slot 없음 = 커스텀
  ]
}
```
- 규칙: `top_items[i].slot`이 표준 7슬롯이면 **표준 연결 항목**(값은 `cell_map[slot]`/의미 파이프라인), 없으면 **커스텀 항목**(`custom_slots[id]`/`custom_fields[id]`).
- `top_items[i].label`은 사용자 표시용. 표준 항목 라벨 변경은 **생성 결과에 영향 없음**(양식 인쇄 라벨은 HWPX 템플릿에 있음). 커스텀 항목 라벨은 2단계 입력 필드 라벨로 쓰인다.
- `top_items[i].cell`은 저장하지 않아도 된다 — 표준은 `cell_map[slot]`에서, 커스텀은 `custom_slots[].cell`에서 도출된다(단일 진실 원천 유지). 순서는 `order`(또는 배열 인덱스)로만 표현.

#### 후방호환 마이그레이션
- **로드 시(v1·v2 → 편집기)**: `top_items`가 없으면 즉석에서 합성한다 — `cell_map`의 표준 슬롯을 `MN_SLOT_ORDER` 순서로 표준 항목화(라벨=`MN_SLOT_LABELS[slot]`) + `custom_slots`를 커스텀 항목화. 즉 **기존 파일도 동일한 리스트로 보인다**(별도 변환 저장 불필요).
- **저장 시(편집기 → v3)**: `top_items`를 기록하되, 동시에 **표준 항목 → `cell_map`, 커스텀 항목 → `custom_slots`로 환원**해 함께 저장한다. 따라서 v3 파일도 기존 로더(`load_minutes_cellmap`, `generate_minutes`)가 `cell_map`/`custom_slots`만 읽어도 정상 동작한다(이중 안전).
- **다운그레이드 안전**: v3을 모르는 구버전 코드가 열어도 `cell_map`/`custom_slots`가 그대로 있어 생성에 지장 없다. `top_items`는 단지 무시된다.
- **검증 재사용**: 저장 경로는 기존 `save_minutes_cellmap`을 그대로 쓴다. 필요 시 `top_items` 검증(`_validate_top_items`)을 추가하되, **표준 슬롯 화이트리스트 = `MINUTES_SLOTS`** 재사용, 커스텀 id 유일성은 기존 `_validate_custom_slots` 규칙과 일치시킨다.

> 과설계 경계: `top_items`는 **순서+라벨+종류**만 담는 얇은 레이어다. 셀 좌표·값 공급은 기존 `cell_map`/`custom_slots`가 단일 출처다. 좌표를 `top_items`에도 중복 저장하지 않는다(이중 진실 원천 방지).

> **구현 노트 (v1.0 실제 구현 — 더 단순한 안 채택):** 위 `top_items`/version 3 스키마는 **불필요**해서 도입하지 않았다. 기존 `annotations` 배열이 이미 ① 배열 순서, ② 표준 슬롯과 별개의 커스텀 `label`(슬롯이 있어도 함께 보존, `_validate_annotations` 257~298행), ③ 좌표·nx/ny를 전부 round-trip 저장한다. 따라서 요구사항 1은 **백엔드·스키마 무변경**으로, 우측 패널을 `annotations` 기반 편집형 리스트로 바꾸는 **순수 프런트엔드** 작업만으로 달성했다.
> - 이름변경 = `annotation.label` 덮어쓰기(표준 항목은 표시 라벨만 바뀌고 `slot`→`cell_map` 값 공급 불변), 순서 = 배열 재배치, 삭제 = 배열 제거, 추가 = 기존 캔버스 클릭 핀.
> - 표시 라벨 우선순위 `mnItemLabel(a) = a.label || MN_SLOT_LABELS[a.slot]` (app.js).
> - **남은 후속(필요 시):** 커스텀 항목의 *출력* 연결 — `saveMinutesMapping`은 아직 `custom_slots`에 `[]`를 보내고 2단계에 커스텀 값 입력 칸이 없어, 커스텀 항목은 편집·저장은 되나 생성물 셀에는 기록되지 않는다(기존 동작과 동일, 회귀 아님). 커스텀 값 출력이 필요해지면 `custom_slots` 환원 저장 + 2단계 입력 칸을 추가한다.

### 데이터 모델 — 요구사항 2 (블록 ↔ 텍스트)
- 저장 포맷 변경 **없음**. `minutes.json`·payload의 `sections:[{type,text}]` 구조는 그대로다. 텍스트는 UI 표현일 뿐, 경계(생성 호출)에서는 항상 `sections`로 환원된다.
- 왕복 호환: `parseSectionsText`·`sectionsToText`가 4서식 ↔ 마크업을 손실 없이 변환. 기존에 저장된 블록 데이터(드롭다운으로 만든 `sections`)도 `sectionsToText`로 텍스트에 채워져 그대로 편집 가능.

### 기술 트레이드오프 — 요구사항 2 구현 방식

| 항목 | (권장) textarea + 라이트 파서 | (대안) contenteditable WYSIWYG |
|---|---|---|
| 외부 의존성 | 없음(앱 원칙 준수) | 사실상 라이브러리 필요(원칙 위배) 또는 대량 자체 구현 |
| 왕복(블록↔텍스트) | 순수 함수 2개로 안정적·테스트 용이 | DOM↔모델 직렬화 복잡, 붙여넣기 정규화 난제 |
| 붙여넣기·IME(한글) | textarea 기본 동작에 위임(안전) | caret·조합 입력·서식 오염 처리 부담 |
| 시각적 서식 표시 | 없음(마크업 기호로만) | 실시간 스타일링 가능 |
| 구현 비용/위험 | 낮음 | 높음 |

**결론: `<textarea>` + 정규식 라인 파서 채택.** 시각적 실시간 스타일이 필요하면 입력 아래 읽기 전용 미리보기 div를 다는 정도로 충분(P2, "필요 시"). contenteditable은 앱의 "외부 의존성 최소·바닐라" 원칙과 충돌하고 IME/붙여넣기 리스크가 커 비채택.

### 확장성·성능
- 항목 리스트는 양식당 수~수십 개. 배열 순회로 충분, 인덱스/DB 불필요.
- 텍스트 파싱은 회의록 1건 분량(수십~수백 줄)의 가벼운 정규식 라인 처리. 입력 중 매 키 파싱은 불필요 — **생성·전환 시점에만** 파싱한다.

### 잠재적 도전 과제
- 요구사항 1: 표준 항목 라벨 변경이 "생성 결과를 바꾼다"고 사용자가 오해할 수 있음 → UI에 "라벨은 표시용, 값은 자동 연결" 힌트 노출.
- 요구사항 2: 마크업 규칙이 직관적이지 않으면 사용자가 서식을 잘못 표현 → textarea 상단/placeholder에 4규칙 예시를 항상 노출. 마커 없는 줄은 `bullet`로 관대하게 처리.
- 요구사항 2: 들여쓰기(공백 vs 탭) 혼용 → 파서가 "선행 공백/탭 2칸 이상"을 `sub`로 일관 처리하고, 직렬화는 공백 2칸으로 정규화.

### 회귀 위험·테스트 고려사항
- **불변 보장(최우선)**: 동일 입력 → 동일 HWPX. 기존 `tests/test_minutes.py`·`test_minutes_api.py`·`test_minutes_store.py`·`test_hwpx_scan.py` 전부 그린 유지.
- 신규 단위/통합 테스트(권장):
  - `parseSectionsText`/`sectionsToText` **왕복**: 4서식 혼합 + 빈 줄 + 들여쓰기 혼용 → 직렬화→파싱→직렬화 동일. (브라우저 의존 없는 순수 함수이므로 작은 JS 자체검증 또는 Node로 1회 실행 가능.)
  - 기존 블록 `sections` → `sectionsToText` → `parseSectionsText` 라운드트립이 원본 `sections`와 의미 동일.
  - v1/v2 fieldmap 로드 → 편집기 `top_items` 합성 → v3 저장 후 `cell_map`/`custom_slots`가 기존과 동일(표준 슬롯 매핑 불변).
  - 표준 항목 라벨 변경 후 생성 → HWPX 셀 값 불변(라벨은 결과 무영향) 확인.
  - 커스텀 항목 추가 → `custom_slots` 저장 → `build_minutes`가 `custom_fields`를 지정 셀에 기록(기존 259~268행 경로) 회귀.
  - `#mn-memo` 처방 후 메모 카드가 짧은 입력에서 과도한 빈 여백 없이 렌더(렌더러 실제 확인 — 정적 점검 아님).
- 수동 검증(렌더 그라운딩): 매핑 모달·2단계 텍스트·메모 카드를 실제 pywebview 렌더에서 열어 눈으로 확인 후 수정.

### 의도적으로 다루지 않는 것 (명시)
- 이미지-핀 클릭/셀 역추적 메커니즘 자체(요구사항 1은 우측 패널 데이터·표시만).
- 회의 내용의 리치 텍스트·표·이미지(요구사항 2는 4서식 한정).
- 메모 카드의 자동 높이 증가(3-B는 P2 "필요 시").
- 견적서(.hwp) 경로 적용.
- `build_minutes`·`generate_minutes`·`scan_hwpx_grid` 변경.
- `top_items`에 좌표 중복 저장·동적 AI 연동 커스텀 필드(MINUTES_SCHEMA 확장)는 후속.

## 10. 사용자 스토리

### A. 상단 고정 항목 (요구사항 1)

- **US-001 — 표준 항목을 기본 프리셋으로 표시**
  - 설명: 작성자로서, 매핑 편집을 열면 표준 항목(사업명·일시·장소·주제·참석자·총인원·회의내용)이 기본 항목 리스트로 채워져 시작점을 갖고 싶다.
  - 수용 기준:
    - 매핑 모달 우측에 표준 항목이 `MN_SLOT_ORDER` 순서로 리스트에 표시된다.
    - 각 항목 행에 라벨·매핑 셀(또는 "미지정")·액션(이름변경·삭제·위/아래)이 보인다.
    - 기존(v1/v2) fieldmap을 가진 양식도 동일 리스트로 합성되어 보인다(별도 저장 없이).

- **US-002 — 항목 이름변경**
  - 설명: 작성자로서, 항목 라벨을 내 양식에 맞게 바꾸고 싶다.
  - 수용 기준:
    - 표준·커스텀 항목 모두 라벨을 인라인 편집할 수 있다.
    - 표준 항목 라벨을 바꿔도 의미 슬롯(`slot`)은 유지되어 값 공급원이 끊기지 않는다.
    - 저장 후 재오픈 시 변경한 라벨이 복원된다.

- **US-003 — 커스텀 항목 추가**
  - 설명: 작성자로서, 표준에 없는 칸(예: 배석자)을 새 항목으로 추가하고 양식 그림에서 셀을 클릭해 연결하고 싶다.
  - 수용 기준:
    - "＋ 항목 추가"로 라벨을 입력해 커스텀 항목을 만든다.
    - 캔버스에서 셀을 클릭(기존 핀 메커니즘)하면 해당 (row,col)이 그 항목에 연결된다.
    - 저장 시 커스텀 항목이 `custom_slots:[{id,label,cell}]`로 기록된다.

- **US-004 — 항목 삭제**
  - 설명: 작성자로서, 내 양식에 없는 항목(예: 총 인원)을 리스트에서 지우고 싶다.
  - 수용 기준:
    - 표준·커스텀 항목 모두 삭제할 수 있다.
    - 표준 항목 삭제 시 해당 슬롯이 `cell_map`에서 제외되고, 생성 시 빈 칸으로 안전 처리된다(기존 미매핑 정책).
    - 삭제는 저장 전까지 모달 내에서만 반영되며, 저장으로 확정된다.

- **US-005 — 항목 순서변경**
  - 설명: 작성자로서, 항목 순서를 내 양식 모양대로 정렬하고 싶다.
  - 수용 기준:
    - 위/아래 버튼으로 항목 순서를 바꿀 수 있다.
    - 변경된 순서가 `top_items`(order/배열)로 저장되고 재오픈 시 유지된다.

- **US-006 — 통합 스키마 저장·환원**
  - 설명: 작성자로서, 편집한 항목 세트가 저장되고 다음에 같은 양식을 쓸 때 그대로 재사용되길 원한다.
  - 수용 기준:
    - 저장 시 표준 항목 → `cell_map`, 커스텀 항목 → `custom_slots`, 전체 → `top_items(version 3)`로 함께 기록된다.
    - `save_minutes_cellmap` 시그니처는 변하지 않는다(`custom_slots` 인자에 실제 값 전달).
    - 저장 후 `load_minutes_cellmap`로 동일하게 복원된다(라운드트립).

- **US-007 — 후방호환 로드**
  - 설명: 기존 사용자로서, 예전 v1/v2 fieldmap 양식도 그대로 열리고 동작해야 한다.
  - 수용 기준:
    - v1/v2 파일을 열면 `top_items`가 즉석 합성되어 편집 가능하다.
    - v3로 저장해도 표준 7슬롯 매핑·생성 동작이 불변이다.
    - v3을 모르는 경로(`generate_minutes`)도 `cell_map`/`custom_slots`만 읽어 정상 생성한다.

- **US-008 — 라벨 표시용 안내**
  - 설명: 작성자로서, 표준 항목 라벨 변경이 출력 값을 바꾸지 않는다는 것을 알고 싶다.
  - 수용 기준:
    - 표준 항목 행에 "라벨은 표시용, 값은 자동 연결"임을 알리는 힌트/툴팁이 있다.
    - 라벨만 바꾸고 생성하면 HWPX 셀 값이 변경 전과 동일하다.

### B. 회의 내용 텍스트 편집기 (요구사항 2)

- **US-009 — 글 쓰듯 회의 내용 입력**
  - 설명: 작성자로서, 회의 내용을 드롭다운 없이 텍스트로 자유롭게 작성하고 싶다.
  - 수용 기준:
    - 2단계 회의 내용이 단일 `<textarea>`로 표시된다(블록 행·"＋ 항목 추가" 없음).
    - `#`(제목)·`-`(항목)·들여쓰기 `-`(하위)·빈 줄(빈 줄) 규칙으로 4서식을 표현할 수 있다.
    - 규칙 예시가 placeholder 또는 상단 힌트로 항상 보인다.

- **US-010 — 초안 → 텍스트 채움**
  - 설명: 작성자로서, AI 초안 내용이 텍스트 편집기에 마크업으로 채워진 채로 시작하고 싶다.
  - 수용 기준:
    - 2단계 진입 시 `draft.sections`가 `sectionsToText`로 직렬화되어 textarea에 표시된다.
    - 4서식이 올바른 마크업으로 변환된다(헤더 `#`, 불릿 `-`, 하위 들여쓰기, 빈 줄).

- **US-011 — 텍스트 → 섹션 환원 생성**
  - 설명: 작성자로서, 텍스트로 쓴 회의 내용이 기존과 동일한 HWPX로 생성되길 원한다.
  - 수용 기준:
    - 생성 시 textarea 값이 `parseSectionsText`로 `sections:[{type,text}]`로 환원된다.
    - 환원된 payload가 기존 형태 그대로 `generate_minutes`에 전달되어 백엔드 무변경으로 동작한다.
    - 동일 내용 기준, 텍스트 입력 결과 HWPX가 블록 입력 결과와 동일하다.

- **US-012 — 블록 데이터 호환**
  - 설명: 기존 사용자로서, 예전에 블록으로 만든 회의록을 다시 열어도 텍스트 편집기에서 그대로 이어 쓰고 싶다.
  - 수용 기준:
    - 기존 블록 `sections`가 `sectionsToText`로 textarea에 손실 없이 채워진다.
    - 텍스트→파싱→직렬화 왕복이 원본 섹션과 의미적으로 동일하다(라운드트립 테스트 통과).

### C. 회의 메모 카드 (요구사항 3)

- **US-013 — 메모 카드 여백 정상화**
  - 설명: 작성자로서, 회의 메모칸이 폭을 채우고 내용에 맞는 높이로 보여 화면이 깔끔하길 원한다.
  - 수용 기준:
    - `#mn-memo`가 카드 폭을 가득 채운다(`width:100%`·`box-sizing:border-box`).
    - 짧은 메모 입력 시 카드 하단에 과도한 빈 여백이 남지 않는다(기본 높이 약 5~6줄).
    - 사용자가 필요하면 세로로 크기를 조절할 수 있다(`resize:vertical`).

### 요구사항 2 — 파서/직렬화 골격 (개념)
```js
// 마크업 → 섹션
function parseSectionsText(text){
  return (text || '').split('\n').map(raw=>{
    if(!raw.trim()) return {type:'empty', text:''};
    const m = raw.match(/^(\s*)(#\s+|-\s+)?(.*)$/);
    const indent = m[1].length, marker = m[2]||'', body = m[3].trim();
    if(marker.startsWith('#')) return {type:'header', text:body};
    if(indent>=2)              return {type:'sub',    text:body};
    return {type:'bullet', text:body};   // '-' 또는 마커 없는 줄
  });
}
// 섹션 → 마크업 (왕복 안정: 한 번 정규화되면 동일 복원)
function sectionsToText(sections){
  return (sections||[]).map(s=>{
    if(s.type==='empty')  return '';
    if(s.type==='header') return '# '   + (s.text||'');
    if(s.type==='sub')    return '  - ' + (s.text||'');
    return '- ' + (s.text||'');          // bullet
  }).join('\n');
}
// 자체검증(개념): parseSectionsText(sectionsToText(x)) ≡ x (의미 동일)
```


## 요구사항 4 — 회의내용 라벨 고정 + 본문 포맷 반영 설계

### 4-0. 개요·배경 (사용자 피드백 후속)

요구사항 1~3 구현본을 실제 앱에서 사용한 뒤 두 가지 지시가 들어왔다. 이 섹션은 그 둘을 코드·템플릿 실측 근거로 분석하고 **최소 변경 수정 방향**을 정의한다(엔진 무변경 원칙 유지).

1. **"회의내용은 기본 라벨로 고정시켜라."** 요구사항 1에서 우측 패널을 자유 편집형 리스트로 바꾸면서, 회의 내용(`content`) 슬롯까지 자유 편집(이름변경·삭제·순서변경) 대상에 포함됐다. 이는 PRD v1.0 요구사항 1-B("`content`는 본문 블록이므로 순서변경 대상에서 분리해 별도 고정")에 이미 명시됐으나 **구현에서 누락**된 부분이다.
2. **"텍스트 에디터의 회의 내용이 양식에 반영되지 않는다."** 요구사항 2로 회의 내용을 단일 `textarea`로 바꾼 뒤, 텍스트로 쓴 회의 내용이 생성된 HWPX에 들어가지 않는 사례가 보고됐다. 원인 규명·수정 방향이 필요하다.

설계 철학(재확인): **최소 변경·외부 의존성 0·백엔드(`build_minutes`/`generate_minutes`) 무변경·후방호환 100%.** 4-A와 4-C는 **순수 프런트엔드(app.js)** 수정으로 해결된다(검증으로 입증).

### 4-A. 회의내용 라벨 고정 [신규·수정] · P0

#### 현상·근본 원인 (검증된 라인)
- 우측 항목 리스트는 `mnNamedItems()`(`ui/app.js` 2318~2320행)가 공급한다:
  ```js
  function mnNamedItems() {
    return mnEditor.annotations.filter(a => a.slot || (a.label && a.label.trim()));
  }
  ```
  필터 조건이 `a.slot || label`이므로 **`slot:'content'`인 회의 내용 핀도 통과**해 리스트에 노출된다 → `mnRenameItem`(2321)·`mnReorderItem`(2328)·`mnDeleteItem`(2336)의 자유 편집 대상이 된다. 표시는 `renderSlotStatus`(2343~2365)가 모든 `mnNamedItems()` 항목을 동일한 편집 행(이름 input + ▲▼✕)으로 그린다.
- 즉 회의 내용이 "사업명·일시"와 똑같이 이름변경·삭제·순서변경된다. 사용자 요구는 **회의 내용만은 기본 라벨로 고정**(자유 항목과 분리)이다.

#### 기능 요구사항
- **4-A-1.** `content` 슬롯은 자유 편집 리스트(`mnNamedItems`)에서 **제외**한다. 이름변경·삭제·순서변경 불가.
- **4-A-2.** 회의 내용은 우측 패널 **상단의 읽기전용 고정 행**으로 별도 표시한다. 라벨은 항상 "회의 내용"(기본), 우측에 매핑된 셀 좌표 또는 "미지정"을 보인다. input·✕·▲▼ 액션 없음.
- **4-A-3.** 매핑 연결(핀)은 유지한다 — 기존 캔버스 클릭 핀 메커니즘으로 content 셀을 지정/재지정할 수 있다(고정 행에 "양식에서 회의 내용 칸을 클릭해 지정" 안내). 단 **삭제·리네임 불가**.
- **4-A-4.** content 핀이 항상 `mnEditor.annotations`에 보존되어 `mnDeriveCellMap`이 cell_map에 `content`를 계속 도출하도록 보장한다(4-C의 버그 직결).

#### 영향 함수·수정 방향 (최소 변경, app.js 한정)
| 함수(라인) | 현재 | 수정 |
|---|---|---|
| `mnNamedItems` (2318) | `a.slot \|\| label` | `a.slot !== 'content' && (a.slot \|\| label)` — content를 자유 리스트에서 분리 |
| `mnReorderItem` (2328~2334) | `memo = annotations.filter(a => !(a.slot\|\|label))` → `named.concat(memo)` | **회귀 주의**: content가 named에서 빠지면 memo 필터에도 안 걸려(`slot` 보유) 재배치 시 annotations에서 **소실**된다. `others = annotations.filter(a => !named.includes(a))` 로 바꿔 content+메모핀을 모두 보존 후 `named.concat(others)` |
| `renderSlotStatus` (2343~2365) | 모든 named를 편집 행으로 | 상단에 content 고정 행(읽기전용) 1줄 + 그 아래 자유 항목 리스트 |
| `mnDeriveCellMap` (2081~2087) | 모든 annotation에서 slot 도출 | **무변경** — content 핀이 보존되므로 cell_map['content'] 계속 도출 |

> 과설계 경계: 백엔드·저장 스키마·`annotations` 구조 무변경. content 핀은 기존과 동일한 annotation(그저 UI에서 자유 편집만 차단). `save_minutes_cellmap` 시그니처·검증 무변경.

#### 수용 기준
- 매핑 모달 우측 상단에 "회의 내용" 고정 행이 항상 보이고, 이름 input·삭제·순서 버튼이 없다.
- 자유 항목 리스트(`mnNamedItems`)에 회의 내용이 더 이상 나타나지 않는다.
- content 셀은 캔버스 클릭으로 지정/재지정되며, 그 좌표가 고정 행에 "(r,c)"로 표시된다(미지정 시 "미지정").
- 항목 순서변경(▲▼)을 반복해도 content 핀이 `annotations`에서 소실되지 않는다(저장→재오픈 후 content 매핑 유지).
- 표준 양식(`is_standard`)에서는 content가 항상 기본 좌표(6,1)로 동작한다(변동 없음).

### 4-C. 회의 내용 반영 버그 — 가설·증거·근본 원인·수정 방향

#### 경쟁 가설과 채택/기각 (코드·재현 증거 기반)

- **가설1 (채택) — content 슬롯이 자유 리스트에 포함되어, 삭제/미지정 시 `mnDeriveCellMap`이 content를 cell_map에서 누락 → 커스텀 양식에서 content 셀 미해결 → 본문 미기록.**
  - 증거① (정적): `mnNamedItems`(2318)가 `slot:'content'` 핀을 리스트에 노출 → `mnDeleteItem`(2336)로 삭제 가능. 삭제하면 `mnEditor.annotations`에서 content 핀 제거 → `mnDeriveCellMap`(2081~2085, `a.slot && MN_SLOT_LABELS[a.slot]`)이 content를 도출하지 못함 → `save_minutes_cellmap`이 content 없는 cell_map 저장.
  - 증거② (정적): `generate_minutes`(`src/api.py` 1056~1057행) — 커스텀 양식이면 `cell_map = fm.get('cell_map')`. content가 빠진 cell_map이 `build_minutes`로 전달.
  - 증거③ (정적): `build_minutes`→`_norm_cells`(200~214) — cell_map에 content가 없으면 `cells['content']`는 DEFAULT (6,1)로 폴백. 커스텀 양식에서 (6,1)은 회의 내용 칸이 아닐 수 있음 → `_find_cell(tbl,6,1)`(316행) None → content 쓰기 블록(317~372) **전체 스킵**.
  - 증거④ (재현): 표준 템플릿에 `cell_map={'content':[99,9]}`(미해결 좌표)로 `build_minutes` 호출 → 생성 XML에 본문 텍스트 부재(`'반영되어야할텍스트' in xml == False`), **경고도 없음**(`warnings == []`). content 셀 미해결 시 무경고 소실이 정확히 재현됨.
  - 결론: **채택.** 요구사항 1이 content를 자유 편집 대상으로 노출시킨 것이 회귀의 진원. (표준 양식은 `is_standard`라 cell_map을 무시하고 DEFAULT (6,1)을 쓰므로 영향 없음 — 그래서 표준에서는 정상으로 보이고 커스텀에서만 증상.)

- **가설2 (기각) — `parseSectionsText`가 빈 sections를 만들거나, `cells['content']` 분기 미진입(엔진 측 결함).**
  - 증거: `build_minutes` 직접 재현에서 sections가 content 셀에 정상 기록됨(4-B 재현). `parseSectionsText`(1817~1826) 회로도 정상 — `# `→header, `- `/무마커→bullet, 들여쓰기→sub, 빈 줄→empty. 표준 양식은 항상 (6,1) content 셀이 존재해 분기 진입. **엔진·파서 무결.** 기각.

- **가설3 (기각) — 2단계 textarea가 재진입/초기화로 비워지거나 id 불일치·타이밍.**
  - 증거: `#mn-r-content-text` textarea는 `ui/index.html` 313행에 단일 존재(id 일치, 중복 없음). `renderMinutesReview`(1798)가 진입 시 `sectionsToText(draft.sections)`로 채우고, `collectMinutesPayload`(1839)가 같은 id에서 읽어 `parseSectionsText`로 환원, `generateMinutes`(1874)가 그대로 전달. 표준 양식에서 텍스트는 정상 반영됨(가설2 재현과 동일 경로). 프런트 수집·전달 회로 무결. 기각.

#### 확정된 근본 원인
**회의 내용(`content`) 슬롯이 요구사항 1의 자유 편집 리스트(`mnNamedItems`)에 포함되어 삭제·미지정될 수 있게 된 것**이 근본 원인이다. 커스텀 양식에서 content 핀이 제거되면 `mnDeriveCellMap`→cell_map에서 content가 빠지고, `build_minutes`의 `_norm_cells`가 DEFAULT (6,1)로 폴백하지만 그 좌표가 실제 회의 내용 칸이 아니어서 `_find_cell`이 None을 반환, 본문 쓰기 블록이 통째로 스킵되며 **경고 없이** 회의 내용이 누락된다.

#### 최소 수정 방향 (회귀 위험 포함)
- **1차(핵심): 4-A와 동일한 수정으로 동시 해결.** content를 자유 리스트에서 분리해 삭제 불가 고정 행으로 만들면 content 핀이 항상 보존되어 `mnDeriveCellMap`이 content를 cell_map에 계속 도출한다. **별도 백엔드 수정 불필요.** (프런트 한 군데, app.js)
- **회귀 주의 1**: `mnReorderItem`(2332행) memo 분리 로직 — content를 named에서 빼면 memo 필터(`!(slot||label)`)에도 안 걸려 재배치 시 annotations에서 소실된다. `others = annotations.filter(a => !named.includes(a))`로 교체해 content 보존(4-A 표 참조).
- **회귀 주의 2**: 커스텀 양식에서 사용자가 content 셀을 한 번도 핀으로 지정하지 않은 경우(고정 행 "미지정") 여전히 (6,1) 폴백으로 누락 가능. → 고정 행에 "미지정" 강조 + `generate_minutes`의 기존 미매핑 경고(app.js 1862, `unmapped`)에 content 포함 노출로 가시화(2차, 필요 시). 단 이는 표준 미매핑 정책과 동일한 "빈 칸" 계열이므로 신규 백엔드 변경 없이 안내만으로 충분.
- **방어적 보강(선택, 백엔드 무변경 권장이라 비채택 기본)**: `build_minutes`가 content 셀 미해결 시 무경고 대신 `warnings`에 "회의 내용 셀 미해결 — 본문 누락" 추가. 단 엔진 무변경 원칙상 1차에서는 프런트 경고로 대체한다.

#### 수용 기준 (4-C)
- 커스텀 양식에서 회의 내용을 삭제할 수 없으므로, 텍스트창에 쓴 회의 내용이 항상 생성물 content 셀에 기록된다.
- content 핀이 보존되어 저장→`load_minutes_cellmap`→`generate_minutes` 라운드트립 후에도 cell_map에 content가 유지된다.
- 표준 양식 회귀 0: 동일 입력 → 동일 HWPX(기존 골든 불변).
- content 셀을 한 번도 지정하지 않은 커스텀 양식은 생성 전에 "회의 내용 미지정" 경고가 1회 노출된다.

### 4-D. 사용자 스토리 (요구사항 4)

- **US-015 — 회의 내용 라벨 고정 표시**
  - 설명: 작성자로서, 회의 내용 항목이 다른 항목과 섞여 편집되지 않고 항상 기본 라벨로 고정돼 보이길 원한다.
  - 수용 기준:
    - 매핑 모달 우측 상단에 "회의 내용" 고정 행이 읽기전용으로 항상 표시된다(이름 input·삭제·순서 버튼 없음).
    - 회의 내용이 자유 편집 항목 리스트에 더 이상 나타나지 않는다.
    - 고정 행에 매핑 셀 좌표 또는 "미지정"이 표시된다.

- **US-016 — 회의 내용 삭제·리네임 방지**
  - 설명: 작성자로서, 실수로 회의 내용 항목을 지우거나 이름을 바꿔 본문이 누락되는 일이 없길 원한다.
  - 수용 기준:
    - 회의 내용은 자유 리스트에서 삭제·이름변경·순서변경할 수 없다.
    - 다른 항목을 순서변경(▲▼)·삭제해도 content 핀이 `annotations`에서 소실되지 않는다.
    - 저장→재오픈 후 content 매핑이 유지된다.

- **US-017 — 텍스트 회의 내용의 양식 반영 보장**
  - 설명: 작성자로서, 텍스트창에 쓴 회의 내용이 커스텀 양식에서도 항상 HWPX에 들어가길 원한다.
  - 수용 기준:
    - 커스텀 양식에서 회의 내용을 삭제할 수 없으므로 content 셀 매핑이 항상 유지된다.
    - 텍스트창 본문이 `# 제목`·`- 항목`·들여쓰기 `- 하위`·빈 줄 규칙대로 양식의 ■/•/└/빈줄로 반영된다(4-B 매핑표).
    - 사진표가 있는 표준 content 셀은 사진표가 보존된 채 본문이 채워진다.
    - 표준·커스텀 양식 모두 동일 입력 → 동일 본문 결과(회귀 0).

- **US-018 — 회의 내용 미지정 경고**
  - 설명: 작성자로서, 커스텀 양식에서 회의 내용 칸을 아직 지정하지 않았다면 생성 전에 안내받고 싶다.
  - 수용 기준:
    - content를 한 번도 핀으로 지정하지 않은 커스텀 양식은 생성 시 "회의 내용 미지정 — 빈 칸 생성" 경고가 1회 노출되고, 한 번 더 누르면 진행된다.
    - 표준 양식은 항상 기본 좌표로 동작해 경고가 뜨지 않는다.
