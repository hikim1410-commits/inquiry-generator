## 1부. 견적서↔회의록 비대칭 해소 결정

이 부에서 다루는 네 항목은 모두 "견적서에는 있는데 회의록에는 없다" 또는 "이름과 동작이 어긋난다"는 형태로 리뷰에서 발견됐다. 넷을 한 묶음으로 처리하지 않고 각각 따로 판단한 이유는, 비대칭이라고 해서 전부 "맞추는 게 답"은 아니기 때문이다. 아래에서 항목별로 (1) 지금 상태가 어떤지, (2) 무엇으로 정했는지, (3) 왜 그렇게 정했는지 순서로 적는다.

### 1-1. Drive 자동 업로드

**현상**: 견적서를 생성하면 설정된 Google Drive 폴더로 자동 업로드되는 기능이 있다. 회의록에는 이 기능이 없어서, 회의록을 쓰는 사람은 완성된 파일을 직접 찾아 수동으로 Drive에 올려야 한다.

**결정**: 회의록 생성 흐름에도 Drive 자동 업로드를 추가한다. 이번 릴리스에서 구현되며, 현재 별도 담당(backend-fixer)이 작업 중이다. 이 문서 기준으로는 **"구현됨"**으로 기록한다.

**근거**: Drive 자동 업로드는 문서 종류(견적서냐 회의록이냐)와 무관하게 "완성된 결과물을 팀 공유 폴더에 자동으로 보낸다"는 하나의 공통 기능이다. 견적서에만 있어야 할 이유가 없고, 사용자 입장에서는 "왜 회의록만 수동으로 올려야 하지?"라는 질문이 자연스럽게 나오는 지점이었다. 맞추는 쪽이 맞다.

### 1-2. "분석·적용" 버튼 라벨

**현상**: 설정 화면의 회의록 양식 관리 영역에 있는 버튼(`ui/index.html:563`, id `btn-scan-mn-tpl`)의 라벨이 "분석·적용"으로 되어 있다. 하지만 실제 클릭 시 동작(`ui/app.js:2789-2792`)은 AI가 표 구조를 분석해 적용하는 게 아니라, **매핑 편집기(이미지-핀 화면)를 여는 것**이다. 견적서 쪽의 동명 버튼(`btn-scan-tpl`)은 이름 그대로 AI 분석·적용을 수행하므로, 같은 라벨이 서로 다른 동작을 가리키는 상태다.

**결정**: 회의록 쪽 버튼 라벨을 실제 동작에 맞게 "매핑 편집"으로 수정한다. 이번 릴리스에서 구현한다.

**근거**: 이름과 동작이 어긋나면 사용자가 버튼을 누르기 전에 무슨 일이 일어날지 예측할 수 없다. "분석·적용"이라는 이름을 보고 AI가 뭔가 자동으로 처리해줄 거라 기대했다가 편집 화면이 뜨면 혼란스럽다. 참고로 회의록 양식 갤러리 카드에는 이미 "매핑 편집"이라는 올바른 라벨의 버튼(`ui/app.js:1992`)이 별도로 존재해서, 같은 화면 안에도 서로 다른 라벨이 공존하는 상태였다. 통일하는 쪽이 맞다.

### 1-3. 새 문서 진입 패턴 차이

**현상**: 견적서는 새로 만들 때 분할 버튼을 누르면 바로 편집기가 뜬다. 회의록은 새로 만들 때 먼저 "양식 갤러리"를 거쳐 어떤 발주처 양식을 쓸지 고른 다음에야 작성 화면으로 들어간다. 두 문서 종류의 진입 흐름이 다르다.

**결정**: **의도적 차별로 유지한다.** 견적서 쪽 흐름으로 통일하지 않는다.

**근거**: 이 차이는 실수가 아니라 두 문서의 본질적인 차이에서 나온다. 회의록은 발주처마다 양식(표 구조, 항목 배치)이 다르고, 어떤 양식을 골랐는지가 이후 매핑·생성 결과 전체를 좌우하는 **필수 선행 단계**다. 양식을 정하지 않은 채로 편집기부터 열면 애초에 어떤 칸에 뭘 쓸지가 정의되지 않는다. 반면 견적서는 단일 템플릿을 쓰기 때문에 고를 대상이 없고, 바로 편집기로 들어가는 게 더 빠르다. 즉 "회의록만 한 단계 더 거친다"는 것은 불편이 아니라 문서 구조상 필요한 단계이므로, 억지로 맞추면 오히려 회의록 쪽이 망가진다.

### 1-4. 대시보드 필터 탭

**현상**: 대시보드 필터 탭에 견적서 관련 3종(예: 상태별 견적서 구분)은 있지만 회의록 필터는 없다.

**결정**: **보류(P2)**. 이번 릴리스에서는 손대지 않는다.

**근거**: 현재도 회의록 문서는 카드 배지로 견적서와 구분해서 볼 수 있어, 최소한의 구분 기능은 이미 있다. 필터 탭을 따로 만드는 비용을 지금 들일 만큼 회의록 문서량이 많지 않다. 문서 수가 늘어서 배지만으로 찾기 불편해지는 시점이 오면, 그때 필터 탭을 추가하는 게 순서에 맞다. 지금 만들면 실제로 필요해서가 아니라 "형평성" 때문에 만드는 셈이라 과잉 대응이다.

## 2부. P2 전략 과제

1부가 "지금 눈에 보이는 비대칭을 어떻게 할까"였다면, 2부는 "지금 당장 문제는 아니지만 방치하면 나중에 더 비싸지는 구조적 부채"를 다룬다. 넷 다 지금 착수하지 않는다 — 대신 방향과 "언제 시작할지"를 미리 정해서, 트리거가 왔을 때 다시 논의부터 시작하지 않도록 기록해 둔다.

### E-1. 핀 매핑의 범용 자산화

**문제**: 지금의 매핑 엔진과 항목 슬롯은 "회의록 7슬롯"에 맞춰 하드코딩되어 있다. `build_minutes`는 현재 문서의 **첫 번째 표만** 생성에 반영하고(`src/minutes/hwpx_minutes.py`, 관련 경고는 `ui/app.js:2088`, `ui/app.js:2302`, `ui/app.js:2422`), 좌표(`cell_map`)도 `[row, col]` 2원소로 표 하나를 전제한다. 이 구조는 회의록 전용으로는 잘 동작하지만, 세 번째 문서 유형(예: 공문, 결과보고서)이 필요해지는 순간 재사용할 수 없다.

**권고 방향**: `cell_map` 좌표를 `[table, row, col]` 3원소로 확장하고(표 번호를 명시적으로 다루도록), 슬롯 정의(어떤 항목이 있는지)를 문서 유형별로 선언하는 방식으로 분리한다. 이렇게 하면 매핑 엔진 자체는 문서 유형에 무관한 범용 자산이 되고, 회의록·공문·보고서는 각자 슬롯 목록만 선언하면 된다.

**착수 트리거**: 세 번째 문서 유형에 대한 요구가 실제로 접수될 때. 지금은 문서 유형이 견적서·회의록 둘뿐이라 일반화 비용을 미리 들일 근거가 없다.

### E-2. AI 프로바이더 3사(gemini/openai/anthropic) 유지비

**문제**: 현재 세 개 AI 프로바이더를 raw HTTP 요청으로 직접 관리하고 있다. 프로바이더 하나당 API 스펙 변경, 인증 방식, 에러 처리를 각각 따라가야 해서 유지 비용이 발생한다.

**권고 방향**: 지금 축소(예: 1~2개로 정리)를 결정할 근거가 없다 — 실제로 사용자가 어떤 프로바이더를 얼마나 쓰는지 통계가 없기 때문이다. 우선 `config`에 프로바이더 선택 이력만 쌓아 관찰하고, 그 데이터를 본 뒤에 축소 여부를 판단한다.

**착수 트리거**: 별도 트리거 없음 — 관찰 자체가 다음 단계이며, 관찰 결과가 쌓이면 그때 축소/유지를 재논의한다.

### E-3. 네이밍 부채

**문제**: 세 이름이 서로 다르다. 저장소 이름은 `inquiry generator`, 제품 이름은 "견적서 생성기", 실제 기능 범위는 견적서와 회의록 둘 다다. 이름만 보고는 제품이 뭘 하는지, 지금 뭘 하는지 헷갈린다.

**권고 방향**: 이름을 정리하는 방향은 맞지만, GitHub 저장소 이름 변경은 자동 업데이트 기능(`src/version.py:14`의 `GITHUB_REPO = "bbiyakfather/inquiry-generator"` 상수, 업데이트 로직은 `src/update/updater.py`)과 직접 연결되어 있어 신중해야 한다. 개명 시 확인할 체크리스트를 다음과 같이 남긴다.
  - `src/version.py`의 `GITHUB_REPO` 상수를 새 저장소 경로로 갱신
  - GitHub 저장소 자체의 이름 변경(또는 새 저장소로 이관 시 기존 릴리스 태그 이전)
  - 과거에 배포된 구버전 클라이언트가 옛 저장소 경로로 업데이트를 조회할 때의 호환성 확인(리다이렉트 여부)
  - 릴리스 태그·릴리스 노트에 적힌 저장소 링크 일괄 갱신
  - 설치 안내 문서(`docs/RELEASE.md` 등)의 저장소 경로 갱신
  - 제품 이름(사용자 대면 명칭)과 저장소 이름을 반드시 일치시킬 필요는 없다는 점을 정리 시 함께 확정(예: 저장소 이름은 유지하고 표시 이름만 바꾸는 대안도 검토)

**착수 트리거**: 명시적 트리거 없음 — 리네이밍은 비용 대비 시급성이 낮으므로, 별도 계기(예: 브랜드 정리, 신규 문서 유형 추가로 "견적서 생성기"라는 이름이 명백히 틀려지는 시점) 발생 시 이 체크리스트를 참조해 진행한다.

### D-4. 빌드 Python 버전 고정 (표준 = 3.13 / .venv-build)

**문제**: 옛 방침(`lessons.md`, 다른 PC 시절 기록)은 "py -3.12 통일"이었으나, 현 빌드 머신(AIDEN-DESKTOP)에는 3.12가 없고 실제 빌드 venv(`.venv-build`)는 **Python 3.13.14**다. v1.3.x~v1.4.x 정식 릴리스가 전부 3.13 빌드로 출하되어, 문서상 방침과 실제 표준이 이미 갈라져 있었다. 강제 장치가 없으면 어느 쪽으로든 계속 표류한다.

**결정**: 실제 출하 실적이 있는 **3.13을 표준으로 확정**하고, `navion_quote.spec`에 3.13이 아니면 빌드를 중단시키는 가드를 추가한다. 이번 릴리스에서 **구현됨**으로 기록한다. `docs/RELEASE.md`의 빌드 명령도 `.venv-build` 기준으로 갱신.

**근거**: D-4의 본질은 특정 버전이 아니라 "빌드 인터프리터가 표준에서 드리프트하는 것"의 방지다. 방침이 문서로만 존재하면 반드시 어겨지므로 spec 파일 자체에 버전 체크를 넣어 즉시 실패시킨다. 표준을 3.12로 되돌리는 대안은 3.12 설치·venv 재구축 비용이 들고, 이미 3.13 빌드가 사용자 환경에서 검증됐으므로 채택하지 않는다.

## 남는 것 (명시적 비범위)

- 1부에서 "의도적 차별 유지"로 정한 새 문서 진입 패턴은 이번 리뷰의 결론이며, 재검토 시점을 별도로 정하지 않는다(문서 종류가 늘어나 진입 흐름 통일이 실제로 유리해지는 시점이 오면 그때 다시 연다).
- 2부의 네 항목은 모두 "지금 구현하지 않는다"가 결론이다. 이 문서는 방향과 트리거만 남기며, 실제 설계·구현은 각 트리거가 충족된 이후 별도 PRD/작업으로 진행한다.
